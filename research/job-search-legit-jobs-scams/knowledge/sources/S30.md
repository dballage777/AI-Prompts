## Learned points
1. Purpose: the Postings API is a REST API designed to help a company build its own job site. All published postings are also visible on the company's Lever-hosted job site (for example https://jobs.lever.co/leverdemo). — [Documented]
2. Base URLs: global https://api.lever.co/v0/postings/ and EU https://api.eu.lever.co/v0/postings/. HTTPS only ("not available via unencrypted HTTP"). Parameters must be URL-encoded. — [Documented]
3. Sites: each company's postings sit under one site name, usually the company name with no spaces (Lever's own is `lever`). A bot needs the company's Lever site slug, usually visible in its jobs.lever.co URL. There is no cross-company search. — [Documented] (slug discovery [Inferred])
4. List endpoint: `GET /v0/postings/SITE?skip=X&limit=Y`. It returns only published postings and needs no API key; the leverdemo test call returned 200 with no key. Output modes are JSON (recommended), HTML (inline `ul` in `div.lever`), and iframe. The mode is set via the `Accept` header or `?mode=`, and the query parameter wins. — [Documented] (no-key confirmed by test call)
5. List parameters: mode, skip, limit, location, commitment, team, department, level, and group (`location`, `commitment`, or `team`; returns results grouped by category). css and resize are for iframe mode only and must be on the company's allowed list. Multiple values for location, commitment, team, and department are OR'ed and case-sensitive, for example `?location=Oakland&location=Boston`. — [Documented]
6. Single posting: `GET /v0/postings/SITE/POSTING-ID`, JSON only, with the same fields as the list. — [Documented]
7. JSON fields: id, text (title), categories (location, commitment, team, department, allLocations), country (ISO 3166-1 alpha-2 or null; not filterable), opening/openingPlain, description/descriptionPlain, descriptionBody/descriptionBodyPlain, lists (requirements, benefits, etc.), additional/additionalPlain, hostedUrl, applyUrl, workplaceType (unspecified/on-site/remote/hybrid; not filterable), salaryRange (currency, interval, min, max; optional), salaryDescription/salaryDescriptionPlain. — [Documented]
8. Live test findings: the response also included `createdAt` (epoch milliseconds), which is not in the README field table. workplaceType appeared as `onsite` in live data, not `on-site` as documented. 4 of 10 demo postings had salaryRange, for example min 85000, max 175000, currency USD, interval "per-year-salary". The demo `country` was "US". — [Documented] (observed in test call)
9. Apply endpoint: `POST /v0/postings/SITE/POSTING-ID?key=APIKEY`. It requires an API key generated by the company's Lever Super Admin, so it is meant for the employer's own site, not third parties. Required fields are name and email; others include resume (multipart only), phone, org, urls, comments, silent, source, ip, timezone, userAgent, acceptLanguage, referer, consent.marketing, consent.store, and opportunityLocation. — [Documented]
10. Rate limit: application POSTs above 2 per second get HTTP 429, and the limit "may also be changed without warning". Integrators must retry and queue, and Lever calls sending candidates to its hosted application form "best practice". The README states no rate limit for GET requests. — [Documented]
11. What the API does not do: full-text search over open jobs; cross-origin (CORS) requests from sites outside the company's own domains and subdomains; access to internal postings; iframe views for detail or application pages; custom success or error URLs; custom application questions; referral info. — [Documented]
12. Visibility: postings in the `published` state are public and "may be scraped by third parties". All other states are hidden from the API. A posting returned by the API is therefore live on the employer's applicant tracking system, a useful legitimacy signal. — [Documented] (signal [Inferred])
13. Terms: the README contains no separate API terms of use, license grant, or attribution rules for third-party aggregators. Only GitHub footer terms apply to the page. Lever's own terms were not read. — [Documented] (absence observed)
14. Third-party client libraries (PHP, a Gatsby source) are listed, and Lever says it does not endorse or certify them. — [Documented]
15. Bot implication: a bot can make server-side keyless GET calls for a known employer's Lever site to confirm a role is currently published. It should link the user to `hostedUrl` or `applyUrl` on jobs.lever.co rather than submitting applications itself, since the POST endpoint is employer-keyed and rate-limited. — [Inferred]
16. Bot caution: a jobs.lever.co page proves only that some Lever customer published it. The bot should still check that the site slug belongs to the real employer, for example by finding the link from the company's own website, because anyone can become a Lever customer. — [Inferred]

## Limitations / bias
- This is vendor documentation for employers building career sites, not for job aggregators. It gives no explicit permission or terms for third-party bots to consume the GET endpoints. CORS is limited to the employer's own domains, so calls must be made server-side.
- There is no last-updated date. Some details differ from live data (`onsite` vs `on-site`, undocumented `createdAt`).
- GET rate limits are not documented. Keep traffic light.
- github.com blocked plain curl (403). The README was read in full via WebFetch and raw.githubusercontent.com. Only one keyless test call was made.

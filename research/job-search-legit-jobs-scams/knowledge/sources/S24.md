## Learned points
1. Purpose: the API gives a JSON view of a company's offices, departments and published jobs, so the company can build its own careers pages. It supports JSONP (the callback name may contain only letters, numbers, underscore and period). — Documented
2. Auth: job-board data is public, and no GET endpoint needs authentication. Only the application-submission POST needs HTTP Basic Auth with the company's Base64-encoded Job Board API key as the username and no password. — Documented
3. GET endpoints (base `https://boards-api.greenhouse.io/v1/boards/{board_token}`): `/` (board name and content), `/jobs`, `/jobs/{job_id}`, `/offices`, `/offices/{office_id}`, `/departments`, `/departments/{department_id}`, `/sections`, `/sections/{section_id}`, `/education/degrees`, `/education/disciplines`, `/education/schools`. — Documented
4. `GET /jobs` returns every job post with id, internal_job_id, title, updated_at, requisition_id, location.name, absolute_url, language and metadata, plus `meta.total`. With `?content=true` it adds the full description (HTML-entity encoded), departments and offices. — Documented
5. `id` identifies the job post and `internal_job_id` identifies the underlying job. Prospect (talent-pool) posts have a null internal_job_id, so a job-search tool should filter those out to show only real openings. — Documented (filtering advice Inferred)
6. `GET /jobs/{job_id}` also returns company_name, first_published, updated_at, application_deadline, content, absolute_url, and AI-disclosure fields (include_ai_disclaimer, ai_disclaimer, ai_opt_out_request_url). With `?questions=true` it adds the application questions (and location, EEOC compliance and demographic questions where enabled). — Documented
7. Pay transparency: `?pay_transparency=true` on the single-job endpoint adds a `pay_input_ranges` array with min_cents, max_cents, currency_type, title and blurb. The example shows 5000000–7500000 cents USD for an "NYC Salary Range". — Documented
8. `/offices` and `/offices/{id}` accept `render_as=list` (the default, with parent_id and child_ids) or `render_as=tree` (nested children). `/education/schools` accepts `term` (name search) and `page` (100 per page). — Documented
9. Submitting an application: `POST /v1/boards/{board_token}/jobs/{id}` takes multipart form-data or JSON. first_name, last_name and email are required (255 characters or fewer, no URLs in name or phone). Attachments must be pdf, doc, docx, txt or rtf and larger than 0 bytes. The job and board must be live and published. Including country_short_name enables fraud-detection location checks. — Documented
10. Greenhouse warns that the Basic Auth token is a secret key. Form posts should go through the employer's own servers, because a direct client-side post would expose the key. A third-party assistant therefore cannot submit applications on a user's behalf without the employer's key; it should send users to the `absolute_url`. — Documented (implication Inferred)
11. The docs page states no rate limits, caching rules or terms of use for the public GET endpoints. — Documented (absence observed in retrieved text)
12. Live check: `/boards/greenhouse/jobs` without auth returned 20 jobs. Each job had the fields absolute_url, application_deadline, company_name, data_compliance, first_published, id, internal_job_id, language, location, metadata, requisition_id, title and updated_at. The sample absolute_url pointed to `job-boards.greenhouse.io/greenhouse/jobs/...`, and updated_at was 2026-11-13. The list response now includes first_published and company_name, which the docs' list example leaves out. — Documented (own observation)
13. Why it matters for legitimacy: data comes straight from an employer's own applicant-tracking system, and `absolute_url` points to the employer's hosted board or careers page. A bot can link users to the source, show freshness (updated_at, first_published, application_deadline), and show posted pay ranges where offered. — Inferred
14. Caveat: a board_token is just a slug, and anyone can open a Greenhouse account. Having a Greenhouse board does not by itself prove an employer is real. The assistant should still match the company's domain and careers page. — Inferred

## Limitations / bias
- Vendor documentation written for employers, not aggregators. It says nothing about third-party reuse, rate limits or terms. Greenhouse's general terms were not read.
- There is no search across companies. You must already know each employer's board_token.
- Only one live call was made, and pay_transparency output was not tested live.
## Best for
- The technical facts (endpoints, keyless GET, key fields, pay-range field) for an assistant that pulls openings directly from employers' own applicant-tracking boards and links to the source.

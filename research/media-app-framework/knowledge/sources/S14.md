## Learned points
1. [Research] This is a preprint benchmark of 407 human-verified issue-resolution tasks from 19 production open-source mobile apps, each with at least 400 GitHub stars. The apps are Android Native (Java/Kotlin), React Native (TypeScript) and Flutter (Dart). Each task pairs a GitHub issue with executable test patches, validated in Docker.
2. [Research] The task split is very uneven. Android Native has 328 tasks (80.6%) from 14 repos. Flutter has 63 (15.5%) from 2 repos (talawa 12, zulip-flutter 51). React Native has only 16 (3.9%) from 4 repos (artsy/eigen 1, expensify/app 2, NMF-earth/nmf-app 11, rocket.chat.reactnative 2). The authors call the RN figures "indicative only (n=16)".
3. [Research] Four models were tested: Claude Sonnet 4.5, GPT-5.2, Gemini 2.5 Flash and Qwen3-Coder. The harness is the single-pass Agentless pipeline, extended with tree-sitter to handle Java, Kotlin, TypeScript and Dart. It is not an interactive agent with terminal access or iteration.
4. [Research] Overall resolution rates were very low. With automated retrieval: Claude 4.23%, Qwen 3.33%, Gemini 3.24%, GPT 3.23%. With oracle retrieval: Claude 5.69%, GPT 4.53%, Qwen 2.57%, Gemini 1.98%. Under automated retrieval only 28 unique tasks were solved by any model, and 93.1% were solved by none.
5. [Research] Per-framework results (Table 10, share of uniquely resolved tasks against benchmark share). Automated retrieval: Android 67.9% vs 80.6% (0.84x), Flutter 32.1% vs 15.5% (2.07x), React Native 0.0% vs 3.9% (0.00x), meaning no RN task was solved. Oracle retrieval: Android 82.4% (1.02x), Flutter 14.7% (0.95x), React Native 2.9% (0.74x), about 1 of 34 resolved tasks. The authors say these differences "reflect repository architecture and framework conventions rather than underlying language difficulty."
6. [Research] Flutter's overrepresentation is put down to its repos leaning toward single-artifact changes (74.6% source-only) "with strong semantic signals in issue descriptions". RN's failure under automated retrieval is said to mirror "complex multi-layer architectures where cross-file dependency tracing breaks down". Half of RN tasks are multi-artifact, and 25.0% involve Source + Manifest + Config.
7. [Research] Causes of failure: multi-artifact coordination (41% of tasks, at most 0.6% solved), file count (single-file 12.7–15.5% solved vs 0% for 11+ files, which is 30.7% of tasks), and patch size (≤10 lines 14.3–16.1% vs 0% for >500 lines). Resolved patches had a median of 7 lines vs 106 for unresolved. No model solved a hard task under automated retrieval.
8. [Research] Localization is a bottleneck: automated-retrieval recall was 13.8–18.6% with precision 42.9–57.2%. Patch generation is the bigger one: even with oracle files (recall 31.4–55.4% overall, 84.5–100% on single-file tasks), resolution stayed at or below 5.69%. Qwen and Gemini got worse with oracle context because of "over-editing".
9. [Research] Mobile fixes average 12.9 files and 334.6 changed lines (median 5 files), compared with 1.7 files and 32.8 lines for SWE-bench. 20.7% of tasks touch more than one language. 18.8% of RN tasks co-modify TypeScript and JavaScript.
10. [Research] Knowledge each framework needs, by domain: Android tasks need Architecture Components 36.0%, Compose 32.9%, coroutines/Flow 29.6%, platform APIs 16.8% and DI 16.5%. Flutter tasks need widgets/UI 39.7% and async Dart 31.7%. RN tasks need UI framework 43.8%, async 25.0%, architecture components 18.8% and native APIs 12.5%.
11. [Research] iOS-native (Swift/Objective-C) apps were left out on purpose: "the Xcode and Apple SDKs Agreement explicitly prohibits execution on non-Apple-branded hardware, and macOS itself cannot be legally run in standard Linux container environments." Android instrumentation tests needing emulators were also excluded.
12. [Research] Other stated limitations: test-suite coverage may be incomplete, issue/PR pairs don't capture UI design iteration, and the pipeline is single-pass, unlike iterative real-world workflows.
13. [Inferred] This benchmark cannot say whether AI agents do better on React Native or Flutter. RN has 16 tasks from 4 repos, Flutter has 2 repos, and the harness is not an agentic tool like Claude Code. It does support a design rule for this project: keep changes small, single-file and single-artifact where possible, because success falls off sharply with file count, patch size and the mixing of build or manifest files with source.
14. [Inferred] The iOS exclusion independently confirms the no-Mac constraint: you can't build or test iOS code in a Linux container. Any framework choice still needs cloud macOS builds (for example EAS Build) for iOS.

## Limitations or bias
- This is a preprint without peer review. The authors' affiliations and email lines in the HTML appear swapped between two authors, a minor rendering issue.
- The framework comparison is badly underpowered: 16 RN tasks and 2 Flutter repos. Four repos contribute 74.4% of tasks, all Android-heavy.
- It measures single-pass Agentless repair of existing large codebases, not greenfield building with an iterative agent. The models tested are not the newest by late 2026.

## Best used for
- Evidence that AI bug-fixing on mobile repos is hard, with failure patterns (file count, multi-artifact changes). Also a caution against reading per-framework AI-performance claims into this data, and independent confirmation that iOS can't be built in Linux containers.

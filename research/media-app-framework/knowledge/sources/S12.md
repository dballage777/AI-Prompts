## Learned points
1. [Documented] The service is now branded "Expo Update" (part of "Expo Services"), but the CLI commands are still `eas ...`. Setup: `npx expo install expo-updates` then `eas update:configure`. A new Android or iOS build is required before the app can receive updates. Publish with, for example, `eas update --channel production --message "..."`.
2. [Documented] What OTA can change: "non-native pieces (such as JS, styling, and images)". Supported: JS bug fixes, copy, translations, styling and layouts, percentage rollouts, CI publishing, and internal testing. Not supported: native code or native dependencies, app permissions, Expo SDK upgrades, and anything else that needs a new binary. Those go through Expo Build.
3. [Documented] App Store rules: the FAQ says "you need to follow the rules of the platforms and app stores", and that "changes to your app's behavior need to be reviewed". It also notes App Store rules change regularly. No other docs page on App Store OTA rules turned up in the docs index. Store privacy forms are covered on a separate page (point 9).
4. [Documented] How matching works: every build embeds a channel (set in eas.json), a runtime version and a platform. Updates are published to a branch. An update runs on a build only if the platform and runtime version match exactly. A channel links to any branch, by default the branch with the same name. For example, `eas channel:edit production --branch version-2.0` re-points a channel.
5. [Documented] Runtime versions describe the JS-native interface. "Any time native code is updated, we're required to make a new build before publishing an update." There are automatic policies (`sdkVersion`, `appVersion`, `nativeVersion`, `fingerprint`), a custom string, and per-platform overrides, where the platform setting wins. Publishing an update that calls missing native code to a build with the same runtime version will break that build.
6. [Documented] Client behavior: by default the app checks for an update at launch, downloads the manifest and then any missing assets, and runs the new update right away only if both finish before `fallbackToCacheTimeout`. Otherwise it applies the update on the next launch. Custom timing is possible with `useUpdates()`, `checkForUpdateAsync()` and `fetchUpdateAsync()`.
7. [Documented] Deployment patterns: the "two-command flow" (`eas build`, then `eas update --branch production`) is described as fastest, with no pre-production checks, and good for smaller projects. Other patterns: a persistent staging flow (staging and production channels, with GitHub Action publishing), a platform-specific flow, and a branch promotion flow, which needs manual runtime versions.
8. [Documented] Rollback: `eas update:rollback` can re-publish an earlier update or tell clients to run the update embedded in the build. A previous update can also be "republished" like a new commit.
9. [Documented] Store privacy: expo-updates sends an `EAS-Client-ID` (a random per-install ID, not derived from hardware), runtime and platform headers, the channel, current and embedded update IDs, and the last fatal launch error (up to 1,024 characters). These have to be covered in Google Play's Data safety form and Apple's privacy details.
10. [Documented] Billing unit: 1 MAU is one unique install that downloads at least one update in the billing cycle. Installs that only check without downloading count as 0. A reinstall counts again.
11. [Documented] Pricing page: Free is $0/month with updates to 1,000 MAUs, 100 GiB edge bandwidth and 20 GiB storage, plus 15 Android and 15 iOS builds on a low-priority queue. Starter is $19/month plus usage, with 3,000 MAUs then usage-based pricing, 100 GiB bandwidth then $0.10/GiB, and $45 of build credit. Production is $199/month plus usage, with 50,000 MAUs, 1 TiB bandwidth then $0.10/GiB, and $225 of build credit. Enterprise is custom, with 40 TiB bandwidth. All tiers list "Unlimited updates". The per-MAU overage rate was not visible in the page text.
12. [Documented] Bandwidth example: each extra MAU beyond the plan adds 40 MiB of bandwidth. A 10 MB Hermes bundle compresses about 2.6x, to roughly 3.85 MB per update download. The SDK 55 changelog (S11) adds that Hermes bytecode diffing cuts download size by about 75%, opt-in in SDK 55 and on by default from SDK 56.
13. [Documented] Testing tracks (review overview): Google Play internal testing allows up to 100 testers, and closed and open tracks allow more. TestFlight allows up to 100 internal team members and up to 10,000 external testers. Both need release builds. The page says Expo Go "is not useful for the review process".
14. [Documented] Expo Update also works in Expo Workflows (`type: update` job) and in GitHub Actions. Classic Updates (`expo publish`) has been deprecated since before December 2021.
15. [Inferred] For a solo developer without a Mac, OTA lets JS and UI fixes (for example recommender UI or prompt-flow screens) reach both platforms without a new store review cycle. Adding a native module (payments SDK, PiP config) still needs a new cloud build and a store submission. At launch scale, the Free tier's 1,000 updating MAUs is the main limit.

## Limitations or bias
- These are vendor docs and pricing, and they promote Expo's own service. Prices can change, and the overage per MAU was not shown in the page text.
- The docs don't quote Apple's actual guideline text on code downloads. Check Apple's App Review Guidelines directly.
- The bandwidth page has a typo ("50,0000 MAU") in its example.

## Summary-only items
- The per-MAU overage price is behind "usage-based pricing" with no visible rate, so it is not recorded.

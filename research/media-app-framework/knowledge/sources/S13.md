## Learned points
1. [Reported] Software Mansion (maintainers of Reanimated, Gesture Handler and Screens) picks a stack by asking five questions: what ships and by when, what is holding the current app back, what the core features are and how they work, where the product is heading, and who maintains it. They frame the choice as a spectrum: React Native as the foundation, React Native with native modules, or fully native.
2. [Reported] React Native as the foundation is recommended when both platforms share much of the UI and the team benefits from frequent updates. Ready-made libraries, Expo's SDK, Fast Refresh, React Native DevTools, EAS builds and distribution, and EAS Update for JS and asset OTA are all cited. They repeat that "changes at the native level still require a new build."
3. [Reported] The hybrid approach (React Native plus native modules) is suggested for apps with "specialized experiences such as interactive maps, media processing, or custom gestures". Turbo Native Modules and Fabric Native Components are the integration points.
4. [Reported] Fully native fits when "closely linked, demanding interactions account for a large part of the product". Business logic can still be shared through Kotlin Multiplatform with separate SwiftUI and Jetpack Compose UIs, or through compatible Swift modules via the Swift SDK for Android.
5. [Reported] KMP vs RN (from the FAQ): choose RN for one codebase for UI and logic, a "very mature library ecosystem", a large community and OTA updates. They add that "AI coding agents know it well thanks to the amount of public React Native code." Choose KMP when the questions point to native but you still want to share code. Shared Kotlin compiles to JVM bytecode or native code, gives smaller apps, strict typing and real multithreading, and the UI can optionally be shared with Compose Multiplatform. An RN app can also call KMP logic through native modules.
6. [Reported] Gobi (maps, AI-assistant suggestions, draggable sheets) had frame drops short of its 120 FPS goal. Fixes came in steps: an open-source native React Native Bottom Sheet, then a custom native map module replacing RN Mapbox, then moving camera-driven marker generation into native code. That reached 120 FPS without cutting the number of map items.
7. [Reported] They then migrated all of Gobi to Swift and Kotlin because maintaining a growing set of bridged native modules "was going to cost more than moving the existing code into native once." The main transition took "around eleven weeks", with new features still shipping. Unmigrated screens ran as "React islands", separate AppRegistry root views inside native screens.
8. [Reported] The migration removed the OTA path: "The over-the-air JavaScript update path was removed... new client code required an app build." At the end, the React Native runtime, Expo runtime dependencies, Hermes, Metro and the JS entry points were all removed.
9. [Reported] AI agents in the migration: work was split into small reviewable tasks "with clear boundaries, existing implementations to refer to, and a number of checks". Developers owned the architecture and the reviews. One developer took Android and the shared contracts, another took iOS, and both followed the same plan. Both platforms were tested against the same recorded event sequences, for example for streamed AI-chat replies.
10. [Reported] Visual and interaction parity was checked by agents using Argent (Software Mansion's toolkit for driving apps), a "visual-parity skill" for comparing screenshots, and ImageMagick pixel diffs. "Implementation and verification became largely automatic for simpler features."
11. [Reported] Counter-examples where RN stayed: Filament (chat) kept RN with a native rich-text input (React Native Enriched) and native Android notifications, cutting Android cold start from 6–10 s to about 800 ms and app size by over 30%. At SeaPeople, crashes and battery drain were not the stack's fault. Fixing background tasks and a re-render loop cut CPU on an iPhone 13 from 170% to 30% and raised crash-free sessions from 95% to about 99%.
12. [Reported] Vibecode built a native SwiftUI iOS host that embeds RN to run user-generated Expo apps as JS bundles. RN's Element Inspector "gives the AI agent structured information about the UI it is editing."
13. [Reported] Their takeaway: choose RN to share screens and logic and move fast, add native code where specific features need it, consider fully native when direct platform control matters across much of the app, and migrate gradually if needed. In the Gobi post's words: "Not always".
14. [Inferred] For a recommender with trailer playback, subscriptions and LLM chat (lists, detail pages, a video player), the "RN as foundation" profile fits better than Gobi's map-heavy, 120 FPS workload. The posts' own criteria suggest RN plus a few native modules is the likely ceiling. Note too that a later move to native would cost the EAS Update OTA path.
15. [Inferred] The posts don't cover solo developers, Mac-free workflows, costs or store submission. Their AI-agent method (small tasks, reference implementations, automated checks, screenshot parity) can be reused with Claude Code. But Argent-style on-device checks for iOS need a running iOS simulator or device, which this project doesn't have locally.

## Limitations or bias
- These are agency marketing posts that end in sales pitches ("Let's talk about your app"). Software Mansion maintains core RN libraries and sells both RN and native services, so it has a stake in either result.
- The performance numbers are self-reported client results, without methods or independent checks.
- The cases involve funded teams with specialist mobile engineers, not solo developers. Team size for Gobi is not stated beyond the two developers on the AI-chat feature.

## Learned points
1. [Documented] The schedule table, as of the read: 0.90.x (branch cut 2027-01-04, release 2027-02-08) Future; 0.89.x (cut 2026-11-02, release 2026-12-07) Future; 0.88.x (released 2026-10-15) Active; 0.87.x (2026-08-11) Active; 0.86.x (2026-06-09) End of Cycle; 0.85.x and everything older down to 0.77.x Unsupported.
2. [Documented] Cadence: each branch is cut about every two months (for example, 2026-01-05, 03-02, 05-04, 07-06, 09-07, 11-02), and the stable release follows about five weeks later. That works out to about six minor releases a year.
3. [Documented] "Commitment to Stability": the project is "committed to maintain the latest 3 minor series (e.g. 0.78.x, 0.77.x and 0.76.x when 0.78 is the latest release)", with "regular updates and bug fixes". The detailed policy lives in the react-native-releases working group.
4. [Documented] Support levels. Future means release candidates come out at a high pace after the branch cut. Active means frequent patches, with the latest stable getting top priority and several quick patches right after .0. End of Cycle means fewer patches unless an important regression needs fixing, plus one last patch before the version moves to Unsupported. Unsupported means "no new released are to be expected. Only very important regressions might create exceptions", and the page says to "upgrade as soon as possible".
5. [Inferred] With about six releases a year and three supported minors, a given RN minor gets roughly six months of support. To stay on a supported version, an app has to move up a minor version at least about every six months.
6. [Documented] Release channels (npm dist-tags): `latest` is stable and meant for production; `next` holds release candidates (`0.79.0-rc.0` style); `nightly` comes daily from `main` of `react/react-native`. App developers "should not need to worry about release channels other than `latest`".
7. [Documented] Versioning follows a 0.x.y scheme. Breaking changes and new features ship only in minor versions (x), and critical bug fixes ship in patches (y). Every breaking change is listed in the CHANGELOG's Breaking and Removed sections and in the "Breaking Changes" section of the release blog post.
8. [Documented] RN counts the following as breaking: incompatible JS, Java, Kotlin, Obj-C or C++ API changes; non-backward-compatible codegen changes; significant behavior changes; removing a dev-experience feature; major bumps of transitive dependencies (for example, React 18 to 19, or Android Target SDK 34 to 35); and raising minimum platform versions (for example, min Android SDK 21 to 23, or min iOS 15.1).
9. [Documented] RN does not count the following as breaking: `unstable_`-prefixed APIs, private or internal APIs (including `@FrameworkAPI` classes), tooling and framework-integration APIs (Metro, DevTools; these changes are "discussed directly with the affected tools"), and development warnings.
10. [Documented] Deprecation cycle: a deprecated API stays available for the next stable release. Deprecated in 0.76 means still present in 0.77 and removed no earlier than 0.78. Some deprecated APIs stay longer, with warnings.
11. [Documented] The Branches page lists the components pinned to each release. For example: 0.88-stable ships React 19.2.3, Hermes V1 `v260318099.0.2`, no legacy Hermes, and the DevTools frontend chromium/7103 (Chrome 136). 0.86-stable is the last branch in the table that lists both legacy Hermes (`v0.17.0`) and Hermes V1. 0.81 is the last branch without Hermes V1.
12. [Documented] The Versions page lists docs for "Next" (main), the current 0.88, and previous versions 0.87 back to 0.77. 0.76 and earlier (down to 0.60) are "Archived versions" hosted on separate snapshot sites. Below 0.60 is the "React Native Archive".
13. [Documented] The Overview footer still says "Copyright © Meta Platforms, Inc.", and the nightly channel is built from `react/react-native`, which matches the move to the `react` GitHub org (see S8).
14. [Inferred] For a solo developer using Expo, the RN support window matters less directly than the Expo SDK's own support policy, because each Expo SDK pins one RN minor (see S8 for the mapping). Even so, falling behind RN's three-minor window means no upstream fixes. The project needs a planned upgrade at least twice a year.

## Limitations or bias
- This is the project's own policy text. The detailed support policy (the react-native-releases working group on github.com) was not read, because GitHub HTML is blocked.
- The Overview's "Last updated" date (Jul 27, 2026) does not match its table contents. The release dates in the table differ by a few days from the blog dates (0.88: table 2026-10-15, blog 2026-10-19).
- The 0.89 and 0.90 dates are planned dates and may change.

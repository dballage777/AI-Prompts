## Learned points
1. [Documented] Shopify went "all-in on React Native" in 2020 for three reasons: stop building features twice, let developers work across the stack, and spend less time chasing feature parity. The post says RN "consistently delivered these benefits". The costs it lists were performance optimization, foundational work, and "keeping up with framework updates and external dependencies".
2. [Documented] The stated reason for leaving RN is that coding agents changed the economics. "By late 2025", LLMs made Shopify question "whether building software twice still meant doing twice the work". In prototypes, agents implemented features on Android using the iOS version as a reference, and vice versa. They also helped developers work outside their primary stack and cut the cost of parity "through shared specifications, tests, and review checkpoints". The post adds that native "still means building and maintaining software on two platforms, that cost has not disappeared."
3. [Documented] Shopify is explicit that this is not a claim that React Native is slow: "React Native apps can be fast. Ours are." The argued benefits of native are being closer to platform capabilities and first-party tooling, with "fewer framework and dependency layers".
4. [Documented] What happens to Shopify's RN libraries. React Native Skia: Shopify sponsors it through the end of 2026, then William Candillon will fork it under a new name and the original repo will be archived. FlashList (about 2M downloads/week, "the default way to render high-performance lists in React Native"): Shopify "will continue to fix critical issues that break compatibility" and is in talks with companies about long-term stewardship. Restyle: being archived, kept working through the end of 2026, then unmaintained, though open to forks.
5. [Documented] Migration strategy: a greenfield rebuild in Swift and Kotlin, not a gradual brownfield migration. The reasons given: LLMs are good at rebuilding from the RN version as a reference, a clean slate, and prototypes that were "substantially faster". The Shopify app (300+ screens, widgets, Apple Watch, Siri Shortcuts) is underway and set to "ship later this year". Point of Sale and Inbox follow.
6. [Documented] The Shop app went from proof of concept to a fully native app published in the stores "in just 12 weeks". The proof of concept was one engineer working with agents for one week on a SwiftUI port. After that, "a core group of six engineers" built the foundations and main user journeys, and feature teams joined midway.
7. [Documented] Helix is Shopify's anti-"slop" system. The post says one-shotting a port from specs "doesn't work" and produces "a huge amount of unmaintainable code". Helix reads the RN code for a screen and proposes ordered "checkpoints" that can each be reviewed in minutes. Each checkpoint must pass tests, match the running app in a visual review, "survive two adversarial code reviewers", and get human approval before it is committed. Review feedback is remembered, "so the loop gets more autonomous".
8. [Documented] The post names simulators as the main problem for agents: "Agentic control of simulators has been a bottleneck". Agents "couldn't reliably build, test, and iterate". Shopify's own tooling was "slow and brittle". RN hot module reload "helps… but it doesn't solve it" because simulator control relies on the accessibility tree or screenshots. "Agents can make code changes in seconds, but it takes them several minutes to test the output."
9. [Documented] Shopify's fix is an "agent-addressable" architecture. Business logic is fully decoupled from the UI and runs headlessly on desktop, exposed through a CLI. Agents can then inspect state, navigate, and act "in milliseconds instead of minutes" without simulators, and work "autonomously for hours". When a simulator is needed, the CLI drives it in a remote mode without reading the layout or accessibility tree.
10. [Documented] Shop app results, native vs RN. Cold start: iOS 2466 ms vs 3200 ms (−23%), Android 2233 ms vs 4433 ms (−50%). Session stability went from 99.5%+ to 99.95%+ ("10x reduction in sessions that crash"). App size: iOS 68 MB vs 67 MB (+1 MB), Android 184 MB vs 293 MB (−109 MB, −37.2%). Android release build time fell about 75%, while iOS stayed about the same. Native Android reached 120 FPS on a Pixel.
11. [Documented] One trigger for the Shop rewrite was the next big RN investment, adopting the New Architecture, which "would have required us to revisit native module integrations, rendering, and the boundaries between shared and platform-specific code."
12. [Documented] Shop tooling: a migration workflow built as an extension for the "Pi coding agent", using subagents for source review, behavior docs, platform plans, implementation, and parity review. Plan approval was tied to a content hash. Tardis is a debugging tool that gives agents structured access to live app events, logs, and state, sends commands, and captures screenshots and event windows from both the RN and native apps for parity checks.
13. [Documented] The post says "Native expertise remained essential". Generated code could meet requirements while "introducing duplication, architectural drift, or performance problems". Linting, tests, static analysis, performance checks, and code review were still required. The learning curve from RN to SwiftUI and Compose was "more manageable than we expected" because of shared declarative UI concepts.
14. [Inferred] For a solo developer, Shopify's conditions do not carry over. It had an existing RN app to use as a translation reference, six or more experienced engineers, custom harnesses (Helix, Tardis, headless CLI), and Macs. Native Swift for iOS also needs Xcode on macOS, and the post does not address cloud or Linux workflows. The transferable lessons are architectural: keep business logic headless and testable outside the UI, give the agent a fast non-simulator feedback loop, and gate agent work with tests and checkpoints.
15. [Inferred] There is an ecosystem risk for RN apps that would depend on Restyle (unmaintained after 2026), Skia (moving to a fork under a new name), or FlashList (stewardship uncertain, though critical fixes continue). A video- and list-heavy recommender app would likely use FlashList.

## Limitations or bias
- This is a single company's self-reported case study and partly a recruiting post ("we're hiring"). The metrics are not independently verified and the methods are only briefly described, for example startup time "from tapping the app icon until the initial home feed content is visible".
- The comparison is confounded: the native rewrite also "deliberately retir[ed] some screens and streamlin[ed] others", and the RN baseline was pre-New Architecture.
- Large-team context with proprietary tooling (Helix, Tardis, Pi extension) that is not public. The post gives no cost or token figures.
- It says nothing about Flutter, KMP, or no-Mac development.

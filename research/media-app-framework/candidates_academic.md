# Candidates: academic and scholarly sources

Topic: choosing a cross-platform mobile framework (React Native with Expo, Flutter, Kotlin Multiplatform, or native) for a solo developer shipping a public Android and iOS app, 2025–2026.
Batch: academic and scholarly (empirical studies, benchmarks, mining studies, theses). Checked 2026-11-25.
Method: WebSearch for candidates, then curl to check status (UA "MediaAppResearch/0.1 (research run)"). For arXiv entries, the title, date, authors and abstract were read from the abstract page metadata. Theses and other papers were checked from their landing page or the first pages of the PDF. Key findings come only from abstracts or text that was actually read.
Format: name (authors, year) | canonical URL | type | why it matters, with key finding | how found | status

## Framework comparisons: performance, resources, quality

1. Cross-Platform vs Native Mobile Development: An Empirical Study of Software Quality Trade-offs (Ilovan, 2026-09) | https://arxiv.org/abs/2609.21544 | arXiv preprint (not peer-reviewed), 19 pp | The only study found that compares native iOS, native Android, Flutter, React Native and KMP on one realistic app (a plant manager: auth, image transfer, lists, sync, media upload). It has 8 runnable variants and 2,000 runs per variant, guided by ISO/IEC 25010. Native had the lowest non-UI client time on both OSes, and KMP was the closest cross-platform option. UI and per-operation rankings varied by task. Shared-code approaches needed less authored source than the two native apps combined. No universal winner. | given in brief; checked | ACCESSIBLE
2. Analyzing the Resource Usage Overhead of Mobile App Development Frameworks (Oliveira, Castor et al., EASE 2023) | https://research.utwente.nl/en/publications/analyzing-the-resource-usage-overhead-of-mobile-app-development-f/ | peer-reviewed conference paper (EASE 2023); foundational | Measured energy, execution time and memory for Flutter, React Native and Ionic against native Java on Android: 10 CPU-heavy benchmarks plus 2 apps. The abstract says cross-platform and hybrid frameworks "can be competitive". Per the conference page snippet, Flutter usually had the least overhead and React Native the most in the benchmarks. Android only. | given in brief; checked | ACCESSIBLE (record and abstract; PDF not downloaded)
3. Ecological Impact of Native versus Cross-Platform Mobile Apps: a Preliminary Study (Frattaroli, Le Goaër, Philippot, ASE 2023 workshop) | https://www.se.cs.uni-saarland.de/conferences/ASE/ase2023/profile/ase-2023/olivierlegoaer.html | peer-reviewed workshop paper; preliminary; foundational | Compared package size, network traffic and battery drain of a boilerplate app built natively and with KMM, React Native and Flutter. Preliminary result: the cross-platform solutions "perform quite well". The 2026 Ilovan study cites it for "native has the smallest packages". Very small sample (one boilerplate app). | WebSearch (energy query) | ACCESSIBLE (conference profile and abstract; the paper file link was not followed)
4. Challenges and solutions in cross-platform mobile development: a qualitative study of Flutter and React Native (Aalto MSc thesis, supervisor Fagerholm, 2024-05) | https://aaltodoc.aalto.fi/items/3ddc2600-0e11-4468-8747-17cf27c3d9aa | master's thesis, open repository | Semi-structured interviews with 20 Flutter and React Native developers about developer experience. Main challenges: performance optimization, UI consistency, native-module integration, the learning curve of a new language, and frequent version updates. Directly relevant to a solo developer's maintenance burden. | WebSearch (GitHub issues query) | ACCESSIBLE
5. A Comparative Analysis of Flutter and Native Mobile Application Development (Fangqi Lin, UvA/VU MSc thesis, 2025-03, with ING) | https://staff.fnwi.uva.nl/a.s.z.belloum/MSctheses/MScthesis_Fangqi_lin.pdf | master's thesis, open PDF | Uses a controlled test app plus a real banking app case study, on iOS and Android. Flutter matched or beat native UI rendering, especially on iOS. Flutter binaries were significantly larger, and resource use was higher in hardware-heavy tasks such as camera and geolocation (especially on iOS). Memory on Android lagged. Recommends hybrid native modules for system features. | WebSearch | ACCESSIBLE
6. Performance Evaluation of Cross-Platform Mobile Frameworks: A Comparative Study of React Native and Flutter (Safavi, Univ. of Padova MSc thesis, 2024/25) | https://thesis.unipd.it/handle/20.500.12608/87277 | master's thesis | Covers CPU, memory, energy, app size, developer experience and community, using a Flutter prototype app. Abstract: Flutter generally beats React Native on CPU and memory (AOT compilation, own rendering engine), while React Native benefits from the larger JavaScript/React developer base. Weak design (one prototype); the full text is reported as restricted. | WebSearch | ACCESSIBLE (record and abstract only)
7. Empirical Evaluation of the Impact of Mobile Development Frameworks on the Application Source Code Quality (Karami, ETS Montréal MA.Sc. thesis, 2023) | https://espace.etsmtl.ca/id/eprint/3209/1/KARAMI_Parsa.pdf | master's thesis, CC licensed; before 2024 but on-topic | A systematic review found that prior comparisons ignored source-code quality and used few apps. The empirical part compares code-quality metrics across a large set of Android Native and React Native apps and concludes that the framework choice affects source-code quality. Useful for the maintainability question. Does not cover Flutter. | WebSearch | ACCESSIBLE
8. Performance analysis of Jetpack Compose components in mobile applications (Kwiatkowski, Smołka, JCSI vol. 37, 2025) | https://ph.pollub.pl/index.php/jcsi/article/download/7914/5284/39320 | peer-reviewed journal article (small Polish CS journal) | Macrobenchmark tests of Compose lists, animations and dispatchers on 3 devices. Specialized components were not always faster. This is native-Android background only, not a framework comparison. | WebSearch (energy query) | ACCESSIBLE

11. On the Adoption of AI Coding Agents in Open-source Android and iOS Development (Khan et al., 2026-02) | https://arxiv.org/abs/2602.12144 | arXiv preprint | Studied 2,901 AI-authored PRs in 193 Android and iOS repositories (AIDev dataset). Android got twice as many agent PRs and had a higher acceptance rate (71% vs 63% for iOS). Routine feature, fix and UI PRs were accepted most often; refactor and build changes did worst. Native only (Java, Kotlin, Swift, Objective-C). | WebSearch | ACCESSIBLE

## AI coding agents and LLMs on mobile code; quality by language

12. MobileDev-Bench: A Benchmark for Issue Resolution in Mobile Application Development (Fakorede et al., 2026-03; v2 abstract) | https://arxiv.org/abs/2603.24946 | arXiv preprint, 30 pp | 407 verified issue tasks from 19 production apps across Android Native (Kotlin/Java), React Native (TypeScript) and Flutter (Dart). Average fix: 12.9 files and 334.6 lines; 41% need changes across source, build config and resources together. Claude Sonnet 4.5, GPT-5.2, Qwen3-Coder and Gemini 2.5 Flash resolved only 3.2–4.2% (at most 5.7% with oracle retrieval). The React Native and Flutter shares are small (per the search snippet on v1: 16 RN and 63 Flutter instances). | given in brief; checked | ACCESSIBLE
13. SWE-Bench Mobile: Can LLM Agents Develop Industry-Level Mobile Applications? (Tian et al., 2026-02) | https://arxiv.org/abs/2602.09540 | arXiv preprint and hosted benchmark | Uses a production Swift/Objective-C iOS codebase with PRD and Figma inputs. Tested 22 agent-model setups (Cursor, Codex, Claude Code, OpenCode). Best task success was 12%. The same model showed up to a 6x gap across agents, and simple "defensive programming" prompts beat complex ones by 7.4%. | given in brief; checked | ACCESSIBLE
14. AppForge: From Assistant to Independent Developer (Ran et al., 2025-10) | https://arxiv.org/abs/2510.07740 | arXiv preprint (under review) | 101 tasks asking a model to build a real Android app from a natural-language spec, with automated functional tests. Across 12 flagship LLMs, the best (GPT-5) produced only 18.8% functionally correct apps. Shows that whole-app generation, with lifecycle, state and async handling, is still weak. | given in brief; checked | ACCESSIBLE
15. AppEval: A Unified Benchmark for LLM-Based Mobile Application Repair in ArkTS, Swift, and Kotlin (Xie et al., 2026-08) | https://arxiv.org/abs/2608.18588 | arXiv preprint, 9 pp | Repair tasks are checked with a build-install-launch-test oracle on real toolchains. The audited Android partition has 200 tasks from 24 repositories. Five agents scored 22.0–90.5% Pass@1, so agent choice dominates. The authors say the iOS results are not yet audited and warn against cross-platform generalization. | given in brief; checked | ACCESSIBLE
16. SwiftEval: Developing a Language-Specific Benchmark for LLM-generated Code Evaluation (Petrukha, Kurliak, Stulova, FORGE 2025, accepted, IEEE) | https://arxiv.org/abs/2505.24324 | peer-reviewed workshop paper (accepted version) | Argues that the Swift parts of MultiPL-E and HumanEval-XL are flawed because they are machine-translated from Python. Introduces 28 hand-crafted Swift problems and evaluates 44 code LLMs. Scores drop sharply on problems that need Swift-specific features, especially for smaller models. | given in brief; checked | ACCESSIBLE
17. Kotlin ML Pack: Technical Report (Titov et al., JetBrains, 2024-05) | https://arxiv.org/abs/2405.19250 | technical report | Releases Kotlin datasets (KStack, KStack-clean, KExercises) and an expert-rewritten Kotlin HumanEval. Fine-tuning on small, high-quality Kotlin data raised the pass rate by up to 16 points. This is evidence that Kotlin was under-served by models at the time. | given in brief; checked | ACCESSIBLE
18. Diffs vs. Whole Files: Iterative Edit-Based vs Direct Generation for Flutter/Dart Code Models (Andrejev, 2026-09) | https://arxiv.org/abs/2609.05779 | arXiv preprint, single author | The only Dart/Flutter-specific LLM code study found. Small models (100M parameters, and Qwen2.5-Coder-0.5B) were trained on about 1,790 held-out Flutter tasks. Whole-file generation beat diff-based edits on compile and analysis pass rate, similarity and LLM-judge quality. Diffs were competitive only on short, localized edits. Limited relevance to frontier assistants. | WebSearch | ACCESSIBLE
19. React-ing to Grace Hopper 200: Five Open-Weights Coding Models, One React Native App (Potanin, 2026-04) | https://arxiv.org/abs/2604.17187 | arXiv preprint, case study (n=1 task) | Five open-weights models built one multi-file React Native app with auth and web support. SWE-Bench rankings did not predict success. Adapting native mobile APIs for the web was a training-data gap for every model tested. Anecdotal but relevant to Expo/RN with AI help. | WebSearch | ACCESSIBLE
20. Bridging Design and Development with Automated Declarative UI Code Generation (DeclarUI; Zhou et al., 2024-09) | https://arxiv.org/abs/2409.11667 | arXiv preprint (later FSE 2025 per common citation; venue not verified here) | Design-to-code tool for React Native using CV, multimodal LLMs and compiler feedback. Reached 98% compilation success and 96.8% page-transition coverage, with a 29% compile gain over plain MLLMs. The abstract says it generalizes to other declarative frameworks. Shows that the RN/TSX target is well supported by multimodal LLMs. | WebSearch | ACCESSIBLE
21. LLMs as Code Generators for Model-Driven Development (Cheon, ICSOFT 2025) | https://www.scitepress.org/PublishedPapers/2025/135803/ | peer-reviewed conference paper | ChatGPT generating Dart/Flutter code from UML and OCL. It implemented the constraints accurately and handled scaffolding well. Gaps remained in verification, performance and modular abstraction. Small qualitative evaluation. | WebSearch | ACCESSIBLE
22. Multi-SWE-bench: A Multilingual Benchmark for Issue Resolving (Zan et al., 2025-04; NeurIPS 2025 D&B per search) | https://arxiv.org/abs/2504.02605 | arXiv preprint and NeurIPS datasets track | 1,632 instances (preprint) in Java, TypeScript, JavaScript, Go, Rust, C and C++. Per the NeurIPS abstract snippet, LLMs do well on Python but generalize poorly to other languages. Gives a TypeScript baseline for the RN/Expo side. Has no Dart, Swift or Kotlin. | WebSearch | ACCESSIBLE
23. SWE-PolyBench: A multi-language benchmark for repository level evaluation of coding agents (Rashid et al., Amazon, 2025-04) | https://arxiv.org/abs/2504.08703 | arXiv preprint | 2,110 instances: Java 165, JavaScript 1,017, TypeScript 729, Python 199. Agents perform unevenly across languages. TypeScript is the only mobile-relevant language covered. | WebSearch | ACCESSIBLE
24. A Survey on LLM-based Code Generation for Low-Resource and Domain-Specific Programming Languages (Joel, Wu, Fard, TOSEM, 2024-10) | https://arxiv.org/abs/2410.03981 | peer-reviewed survey (ACM TOSEM, accepted) | Reviews 111 papers from 2020 to 2024. LLMs score much lower on low-resource languages than on Python. MultiPL-E is a key benchmark, and Swift is among the low-resource languages evaluated (per the search snippet). Background for "how well do assistants know Dart, Swift or Kotlin compared with TypeScript". | WebSearch | ACCESSIBLE
25. Multi-Agent Strategies for Bridging Programming Language Gaps in Code Generation (XL-CoGen; Moumoula et al., TOSEM, 2025-09) | https://arxiv.org/abs/2509.19918 | peer-reviewed journal (TOSEM, accepted) | LLMs are inconsistent across languages; transfer through other languages plus repair gives the largest gains on weak languages. A search snippet suggests per-language tables that include Dart and Kotlin (for example Dart 67.7 vs Kotlin 86.2 in one table). I have not confirmed this from the full text, so check before citing. | WebSearch | ACCESSIBLE (abstract)
26. Kotlin Benchmark (JetBrains blog, 2026-07) | https://blog.jetbrains.com/kotlin/2026/07/introducing-the-kotlin-benchmark-evaluate-ai-coding-agents-on-real-world-kotlin-tasks/ | industry benchmark (grey literature, vendor; not peer-reviewed) | SWE-bench-style benchmark of 105 real Kotlin repository tasks verified in containers. The blog says leading agents complete "a large share" of tasks, with the top result from Claude Code with Opus 4.7. The exact rate was not read; search snippets claim about 76%. Vendor source, so possible bias. | WebSearch | ACCESSIBLE

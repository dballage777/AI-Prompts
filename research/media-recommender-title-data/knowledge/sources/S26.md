## Learned points
1. [Documented] Core concept: "Episode order is the agreement that makes an episode number meaningful." Aired order, DVD order and absolute numbering "can assign different coordinates to the same material". An SxxEyy number is not an identity unless you know which arrangement it belongs to.
2. [Documented] Why mismatches happen: "a filename can be recognized perfectly while its title, synopsis and thumbnail are wrong". The parser reads S01E02 correctly, but the metadata lookup reads that coordinate under a different order. In the worked example (fictional "Harbour Watch"), aired order is A→C→B→D and DVD order is A→B→C→D, so DVD S01E02 ("The Missing Boat") is aired S01E03.
3. [Documented] Recommended resolution chain: (1) establish the series, distinguishing reboots and same-name shows; (2) establish the arrangement; (3) interpret the coordinate within it; (4) associate the resource and confirm the story matches; (5) present the desired sequence. "A correct coordinate under the wrong arrangement produces the wrong child identity."
4. [Documented] There is no constant offset between orders: "an explicit mapping is safer to reason about than a constant offset". A permutation can move episodes in both directions, so "adding one to every number would corrupt the other stories". Translation always goes number → story → number in the target order.
5. [Documented] Sorting and identification are separate. Changing the display sort only rearranges items that are already identified. It "cannot repair" a wrong match, because "Both interpretations already have a number 2".
6. [Documented] Alternate releases can change segmentation, not just order. One 44-minute DVD programme can combine two 22-minute aired episodes, leaving "no single aired coordinate" for it. Recuts that move scenes mean title or runtime matching is not enough. The page cites TheTVDB's alternate season types and multi-segment/DVD policy as concrete cases.
7. [Documented] Specials have both an identity (e.g. S00E03) and a viewing position. "Putting every season-zero item before season one is one possible numeric sort, not a universal narrative order."
8. [Documented] Aired order (Aired page) is a catalogue convention: "TheTVDB's API documentation says its default order is generally aired order." Production order can differ from broadcast order. Production codes are "not automatically a filename-ready episode number". Air dates are "evidence, not the complete key", because of same-day releases, batch streaming drops and regional dates.
9. [Documented] DVD order (DVD page) is a release arrangement, not a file format. Disc numbers ("Season 1, disc 2", "Programme 3 on disc 2", "Bonus disc") are storage positions, not catalogue seasons or episodes. A regional box set can have a different cut, so a general "DVD" label may not be enough.
10. [Documented] Absolute numbering (Absolute page) is a series-wide position. With seasons of 12/10/8 episodes, S02E03 = 12 + 3 = absolute 15, absolute 13 = S02E01 and absolute 23 = S03E01. A fixed "ten per season" formula fails. Whether specials are included shifts the numbers (a special between 12 and 13 becomes 13 in one scheme), and "The integer 13 cannot tell a library which agreement the resource's filename uses."
11. [Documented] Viewer state is tied to identity: a "played flag for story B should not become a played flag for story C just because both occupy coordinate E02 in different arrangements".
12. [Documented] The page's references point to TheTVDB v4 API (season types and alternate orders), TheTVDB multi-segment FAQ, TMDB API "Television episode groups", Emby TV naming and Emby BaseItemDto. Alternate orders are a provider capability (TVDB season types, TMDB episode groups), not something the media server makes up.
13. [Inferred] For the recommender: when telling a user "start at S2E5" or "skip to episode 26", name the order and catalogue (e.g. "TMDB aired order"). For anime, prefer naming the entry or arc over absolute numbers, since TMDB (S13), MAL (S12) and streaming services partition differently. Never convert between orders with arithmetic offsets.

## Learned points
1. [Documented] Recommenders' stated aim is to help "researchers, developers and enthusiasts" prototype, experiment with, and put into production classic and state-of-the-art recommenders. It is organized around five tasks: Prepare Data, Model, Evaluate (offline metrics), Model Select and Optimize, and Operationalize.
2. [Documented] The evaluation module splits metrics into rating metrics (RMSE, MAE, R², explained variance, AUC, logloss), ranking metrics (precision@k, recall@k, r-precision@k, NDCG@k, MAP@k, all with default k=10), and "beyond-accuracy" metrics (catalog coverage, distributional coverage, novelty, diversity, serendipity). The beyond-accuracy metrics have pandas and Spark (`SparkDiversityEvaluation`) versions.
3. [Documented] Catalog coverage is the number of distinct items recommended to all users divided by the number of distinct items in the training data (|N_r|/|N_t|), based on Shani & Gunawardana (2010).
4. [Documented] Distributional coverage is the entropy of how often each item is recommended: −Σ p(i|R)·log2 p(i|R), where p(i|R) is the item's share of all recommendation rows (formula 21 in Shani & Gunawardana). Higher means recommendations are spread more evenly across items. (The notebook's LaTeX writes log2 p(i), but the code uses p(i|R).)
5. [Documented] Item novelty is −log2(interactions with the item / total interactions in training), following Castells, Vargas & Wang (ECIR 2011). High novelty means long-tail items and low novelty means popular head items. List novelty is the average item novelty, weighted by how often each item is recommended. In this library, novelty is a popularity measure, not a measure of whether this user has seen the item.
6. [Documented] Diversity is 1 − intra-list similarity (Ziegler et al. 2005; Zhang et al., Auralist, WSDM 2012). It is the average pairwise cosine similarity of the items in each user's list, averaged over users. Pairs with no similarity entry count as 0.
7. [Documented] There are two item-similarity options. The default, `item_cooccurrence_count`, is |users who liked both| / (√|users who liked i| · √|users who liked j|), which is behavioral. The other, `item_feature_vector`, is cosine similarity on content feature vectors. The notebook notes that diversity and serendipity values change depending on which similarity is used.
8. [Documented] Serendipity follows Zhang et al. (2012) and Eugene Yan (2020). For user u and item i, expectedness(i|u) is the mean similarity between i and every item in u's history. Item serendipity is (1 − expectedness) × relevance, averaged per user and then across users. If no relevance column is given, relevance defaults to 1 for every item, which reduces the measure to plain unexpectedness. The docs say that with relevance it measures "pleasant surprise."
9. [Documented] Notebook evidence (ALS vs. random on MovieLens): ALS beats random on Precision@k, Recall@k, NDCG@k and MAP@k, while random beats ALS on diversity metrics. The stated reason is that accuracy-optimized ALS tends to recommend popular items, which leaves long-tail items less chance of being introduced to users.
10. [Documented] The notebook frames the choice as a trade-off: "Usually there is a trade-off between one type of metric vs. another," and which metrics to optimize should depend on the scenario. It also says long-tail items "suffer from the cold-start problem."
11. [Documented] In the README benchmark (MovieLens, 75/25 stratified split, k=10), BiVAE has the best ranking scores (MAP 0.33, nDCG@10 0.4717, Precision@10 0.4113), then LightGCN (nDCG 0.4191), SAR (0.3938), NCF (0.3931), BPR (0.3623), embdotbias (0.119) and ALS (0.0328). The benchmark reports no diversity or novelty numbers.
12. [Documented] The library lists about 30 algorithms, collaborative filtering (ALS, BPR, SAR, NCF, LightGCN, SASRec, and others) and content-based (TF-IDF, DKN, LightGBM, and others). It has no LLM-based recommender.
13. [Inferred] Coverage and novelty need a catalog and popularity counts (interaction logs). A personal LLM recommender has no such logs, so popularity would have to come from an outside proxy such as rating counts, or from the user's own history.
14. [Inferred] For a prompt-based show/movie/anime recommender, you could check each slate offline: (a) intra-list diversity on genre/tag vectors (feature-vector similarity, since there is no co-occurrence data), (b) unexpectedness = 1 − average similarity to the user's watched list, kept only for items the user later rates well, and (c) mean −log2 popularity to see whether the model keeps falling back on blockbusters.

## Limitations or bias
- The API docs list function signatures but give no formulas. The formulas come from the source code and the example notebook, and the notebook's distributional-coverage LaTeX does not quite match the code.
- All metrics are offline and log-based. Nothing here measures user perception or explanation quality, and nothing covers LLM recommenders or hallucinated items.
- I did not record the notebook's numeric diversity results (I read only the markdown cells). The README benchmark covers accuracy metrics only.
- The project is maintained by its contributors, so it describes its own tooling (it is not neutral evaluation research).

## Learned points
1. [Documented] Two ways to turn caching on: automatic caching = one top-level `"cache_control": {"type": "ephemeral"}` in the request body (breakpoint auto-placed on the last cacheable block and moves forward as the conversation grows); or explicit `cache_control` on individual content blocks. Automatic caching uses one of the 4 breakpoint slots. It is not available on Amazon Bedrock `bedrock-runtime` (400 error there).
2. [Documented] TTLs: `ephemeral` is the only cache type; default lifetime 5 minutes, refreshed free each time the entry is read. 1-hour TTL via `{"type": "ephemeral", "ttl": "1h"}`. Lifetime is counted from the START of the request that writes/reads the entry, so generation time eats into it (a 4-minute stream leaves ~1 minute for the follow-up). No manual cache clearing.
3. [Documented] Multipliers vs base input price: 5-min write 1.25x, 1-hour write 2x, cache read 0.1x on most models; exceptions: 0.05x on Claude Opus 5.5 and Claude Sonnet 5.5, 0.025x on Fable 5.2/5.1 and Mythos 5.2/5.1. Multipliers stack with Batch discount, long-context pricing and data residency. Breakpoints themselves cost nothing.
4. [Documented] Prices per MTok on this page (input / 5m write / 1h write / cache hit / output): Opus 5.5 $4 / $5 / $8 / $0.20 / $20; Sonnet 5.5 $2 / $2.50 / $4 / $0.10 / $10; Haiku 5.5 (prompts up to 100k tokens) $0.10 / $0.125 / $0.20 / $0.01 / $0.50; Haiku 5.5 (prompts over 100k) $0.50 / $0.625 / $1 / $0.05 / $2.50. On a model priced by prompt length, cache reads and writes count toward the prompt length.
5. [Documented] Minimum cacheable prompt length (Claude API, Claude Platform on AWS, Google-managed Google Cloud, Foundry): 512 tokens for Opus 5.5, Sonnet 5.5, Haiku 5.5 (and Opus 5, Fable/Mythos 5.x); 1,024 for Sonnet 5, Sonnet 4.6, Opus 4.8; 2,048 for Opus 4.7; 4,096 for Opus 4.6/4.5, Haiku 4.5. Shorter prompts are silently not cached (no error) — check that `cache_creation_input_tokens` and `cache_read_input_tokens` are not both 0.
6. [Documented] Max 4 explicit breakpoints per request. Prefix order is `tools` → `system` → `messages`; a change at a level invalidates that level and everything after it. Writes happen only at a breakpoint; reads look backward up to 20 blocks (20-block lookback window) for entries earlier requests wrote. On the Claude API a run of consecutive `tool_use` blocks counts as one position, and so does a run of `tool_result` blocks.
7. [Documented] Common mistake called out: putting the breakpoint on a block that changes each request (timestamp, per-request context, incoming user message) — you pay a write every request and never get a read. Put the breakpoint on the last block that is identical across requests. Automatic caching has the same problem in that layout.
8. [Documented] Invalidators: tool definitions (names/descriptions/params) → whole cache; web search or citations toggle → system + messages; `speed` (fast vs standard) → system + messages; `tool_choice` change → messages; adding/removing images anywhere → messages; thinking parameters → messages always (tools/system on some models); `output_config.effort` changes → messages (and on some models tools/system; sending the default explicitly equals omitting it); `disable_parallel_tool_use` change → messages (tool-use page). Also: unstable JSON key ordering in `tool_use` blocks (Swift, Go) breaks caches.
9. [Documented] On Opus 5.5, Sonnet 5.5, Haiku 5.5 (and others listed) you can append a `{"role": "system"}` message mid-conversation instead of editing the top-level `system`, keeping the cache. Beta header `inline-tools-2026-09-15` lets you add/change a tool via a `tool_addition` block without editing `tools`, keeping the prefix cached.
10. [Documented] Usage fields (in `usage`, or the `message_start` event when streaming): `cache_creation_input_tokens` (written), `cache_read_input_tokens` (read), `input_tokens` (only tokens AFTER the last breakpoint — not the total). Total input = sum of the three. A `cache_creation` object splits writes into `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`.
11. [Documented] Rate limits: the 1-hour cache page says "cache hits are not deducted against your rate limit"; the rate-limits page confirms only `input_tokens` + `cache_creation_input_tokens` count toward ITPM, `cache_read_input_tokens` do not.
12. [Documented] Scoping: caches are never shared across organizations; on the Claude API, Claude Platform on AWS and Microsoft Foundry they are also isolated per workspace (each workspace builds its own cache). On Google-managed Google Cloud and Bedrock, isolation is org-only. Hits require 100% identical segments (text and images) up to the breakpoint. Caching does not change output.
13. [Documented] Concurrency: a cache entry is only available after the first response starts; for parallel requests to hit, wait for the first response before sending the rest.
14. [Documented] Mixing TTLs: 1-hour entries must appear before 5-minute entries. Billing positions A (last hit), B (last 1h breakpoint after A), C (last breakpoint): charged reads for A, 1h writes for B−A, 5m writes for C−B.
15. [Documented] Pre-warming: send the request with `max_tokens: 0` — it writes the cache at any breakpoint and returns empty `content`, `stop_reason: "max_tokens"`, no output billed (only the write if not already cached). Rejected with `invalid_request_error` if `stream: true`, `thinking.type: "enabled"`, structured outputs (`output_config.format`), or forced `tool_choice` (`any`/`tool`); not allowed inside Message Batches. Must use an explicit breakpoint on the shared block, and the same thinking/effort config as real traffic.
16. [Documented] When to use 1h: prompts reused less often than every 5 minutes but more often than hourly (e.g., a chat user who may not reply within 5 minutes); if a prompt is used more often than every 5 minutes, stay on 5-min (free refresh).
17. [Documented] Thinking blocks cannot carry `cache_control` but are cached as part of prior assistant turns and count as input tokens when read. On Opus 4.5+ / Sonnet 4.6+ / Haiku 5.5 thinking blocks are preserved even when non-tool-result user content is added, so the cache stays valid.
18. [Documented] Server tools (web search, web fetch, code execution): when the request already has at least one `cache_control`, the API auto-places a 5-minute breakpoint on each server tool result inside the agentic loop; these show up as `ephemeral_5m_input_tokens` even if you only asked for 1h.
19. [Documented] Tools: put `cache_control` on the LAST tool in `tools` to cache all tool definitions; `defer_loading` tools (found via tool search) are appended inline as `tool_reference` blocks and do not break the prefix cache.
20. [Documented] Data retention: ZDR-eligible (excluding "Covered Models"); KV cache representations and hashes are held in memory only and deleted promptly after the TTL. Batch API + caching works, but hits are best-effort.
21. [Inferred] For the media recommender: keep the system prompt + the AniList/TVmaze/Wikidata tool definitions byte-stable and first, with a breakpoint on the last tool or end of system prompt; append per-user taste profile and untrusted tool results after it. Because tool results and user text come after the breakpoint, the static prefix stays cached across all users within one workspace. Needs ≥512 tokens of stable prefix on the 5.5 models.
22. [Inferred] Don't toggle `tool_choice`, effort, images or web search per request (e.g., forcing a tool only in the "verify" step) — that resets the messages cache; split such steps into separate requests or put breakpoints before the variation point.

## Key quotes
- "Prompt caching covers the full prefix: `tools`, `system`, and `messages` (in that order), up to and including the block designated with `cache_control`." — https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- "Shorter prompts cannot be cached, even if marked with `cache_control`. Any requests to cache fewer than this number of tokens are processed without caching, and no error is returned." — https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- "The `input_tokens` field represents only the tokens that come **after the last cache breakpoint** in your request, not all the input tokens you sent." — https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- "When you want to improve your rate limit utilization, because cache hits are not deducted against your rate limit." — https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- "Workspace isolation: On the Claude API, Claude Platform on AWS, and Microsoft Foundry, caches are also isolated between workspaces." — https://platform.claude.com/docs/en/build-with-claude/prompt-caching

## Learned points
1. [Documented] "Never store sensitive API keys in your app code. Anything included in your code could be accessed in plain text by anyone inspecting the app bundle." Tools like `react-native-dotenv` and `react-native-config` are for environment-specific values such as endpoints, and are not server-side secret stores.
2. [Documented] The recommended pattern when the app needs a secret-protected resource is "an orchestration layer between your app and the resource", for example a serverless function (AWS Lambda, Google Cloud Functions) that "can forward the request with the required API key or secret".
3. [Documented] The guide frames itself as "not a preflight checklist" but "a catalogue of options". It recommends investing in security in proportion to data sensitivity, user count and the damage an attacker could do, and closes with "it's significantly harder to access information that was never requested in the first place."
4. [Documented] Storage. Async Storage is unencrypted key-value storage, sandboxed per app, fine for non-sensitive data and Redux/GraphQL state. Do not use it for "Token storage" or "Secrets". Its web equivalent is localStorage.
5. [Documented] Secure storage is not built into React Native. Options: iOS Keychain Services (for tokens, passwords, certificates), Android Encrypted Shared Preferences (plain Shared Preferences are "not encrypted by default"), and Android Keystore for cryptographic keys. Suggested libraries: `expo-secure-store`, `react-native-keychain` ("at your own risk").
6. [Documented] Persisted data (on disk) is more exposed than unpersisted data. Watch for accidental leaks, such as persisting a whole Redux tree that contains sensitive form data, or sending user tokens and personal info to monitoring services like Sentry or Crashlytics.
7. [Documented] Deep links are insecure: "you should never send any sensitive information in them". Any app can register the same URL scheme. On iOS the OS picks silently. Use universal links for secure in-app linking on iOS.
8. [Documented] For OAuth2 in apps, use PKCE (`code_verifier`, a random string, and `code_challenge` = SHA-256 of it), because custom-scheme redirects are not unique. The guide suggests `react-native-app-auth` (PKCE only if the identity provider supports it).
9. [Documented] Always use HTTPS. SSL pinning protects against a malicious root CA installed on the device, but certificates "expire every 1-2 years". When the server certificate changes, apps with the old pinned certificate "will cease to work".
10. [Documented] Networking: React Native provides the Fetch API and `XMLHttpRequest` (so axios and similar work) and WebSockets. Uncaught fetch errors "will be dropped silently", so always catch them.
11. [Documented] iOS enforces App Transport Security (HTTPS required). Cleartext needs `NSAppTransportSecurity` exceptions, preferably per domain via `NSExceptionDomains`. App Store review needs a justification if ATS is disabled with `NSAllowsArbitraryLoads`. Android blocks cleartext by default from API level 28 (`android:usesCleartextTraffic` overrides).
12. [Documented] The XHR security model differs from the web: "there is no concept of CORS in native apps."
13. [Documented] Known fetch issues: `redirect: 'manual'` does not work. Duplicate-name headers on Android keep only the last one. Cookie-based auth "is currently unstable". On iOS, a `Set-Cookie` on a 302 redirect is not set properly, which can cause infinite request loops after session expiry.
14. [Documented] iOS apps can customize the underlying `NSURLSession` (user agent, ephemeral config) with `RCTSetCustomNSURLSessionConfigurationProvider`, called early (in `scene:willConnectToSession:` or `application:didFinishLaunchingWithOptions:`).
15. [Documented] The pages read say nothing about streaming responses with React Native's built-in fetch (for streaming on Expo, see S16 `expo/fetch`).
16. [Inferred] For this app, the Expo API route or another backend is the "orchestration layer" that holds the Claude key. The app should store only its own session or access token in `expo-secure-store`, never in AsyncStorage, and should keep tokens and prompts out of Sentry breadcrumbs.
17. [Inferred] Since native apps have no CORS, CORS headers on the backend do nothing to stop non-browser clients calling the proxy. Abuse prevention must rely on auth, attestation (S17) and rate limits, not origin checks. Prefer bearer-token auth in headers over cookies, given the documented cookie and redirect bugs.

## Limitations or bias
- General guidance, explicitly not exhaustive. It does not cover app attestation, rate limiting or LLM-specific risks. Library suggestions are third-party, "at your own risk".

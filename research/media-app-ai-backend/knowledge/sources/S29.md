## Learned points
1. [Reported] Context: a web developer new to mobile built an Expo/React Native voice-to-appointment app for freelancers. Pipeline: speech to text, text to an LLM, LLM returns structured JSON. The author rejected on-device LLMs (app size, inconsistent performance) and a self-hosted model server (infrastructure cost), and chose an external API (Groq).
2. [Reported] Core argument: Expo/React Native environment variables "are injected into the bundle at build time. They are not truly secret". Anyone with basic reverse-engineering or traffic-inspection skills can extract a key and "burn through your quota and your money". Rule: "Sensitive secrets and privileged API calls must live on a server."
3. [Reported] Recommended architecture: a thin backend whose only job is to hold secrets and forward requests (app to backend to AI provider), hosted on serverless platforms such as Vercel or EAS.
4. [Reported] Expo API Routes: files under `/app` named `*+api.ts` that export HTTP method functions (GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS). Example: `export function GET(request: Request) { return Response.json({ hello: 'world' }) }`. Benefits: one repository, shared TypeScript types between client and server, and local end-to-end development. Limits reported: they still need a separate server deployment, dynamic imports are not supported, ESM-only packages can cause issues, and it is "not a full Node.js server".
5. [Reported] Endpoint protection with Expo AppIntegrity (Google Play Integrity on Android, Apple App Attest on iOS): the app requests an OS-signed integrity proof and sends it with the request; the backend verifies it with the platform; a per-request server-issued challenge prevents replay. The author's framing: from "public endpoint with a secret" to "endpoint that only accepts requests from verified app instances."
6. [Reported] Cost control through monetization: because every AI call costs money, the AI feature is premium-only. RevenueCat manages subscriptions with anonymous app user IDs (no login screen). The backend queries RevenueCat for an active entitlement before each AI call: "the backend never trusts the client".
7. [Reported] Prompt pattern: a system prompt that extracts fixed fields (scheduledDate YYYY-MM-DD, scheduledTime HH:MM, durationMinutes, amountCents, clientName, notes, address). It injects today's date and the user's timezone, uses explicit rules for relative dates, and says "return only JSON". User text is concatenated into the same prompt (`Texto: ${message}`).
8. [Reported] Output handling: the LLM JSON is validated server-side with Zod schemas and rejected on mismatch. "The AI is powerful, but it is still treated as an untrusted input source."
9. [Reported] Full request flow: record, transcribe on device (expo-speech-recognition, using SpeechRecognizer on Android and SFSpeechRecognizer on iOS), send to the backend with the integrity proof and RevenueCat ID, verify integrity, verify entitlement, call Groq, validate JSON, persist.
10. [Reported] Conclusions: the client cannot be trusted; secrets live on the server; paid features are enforced server-side; AI responses are validated like any external input.
11. [Inferred] Gaps relative to this app: the article has no per-user rate limiting or spend caps beyond the entitlement gate, no streaming, no prompt caching, and no prompt-injection defense. User text is interpolated straight into the system prompt. Anonymous RevenueCat IDs are client-supplied, so a free-tier path would still need its own per-device or per-user throttling.
12. [Inferred] The AppIntegrity plus server-side entitlement plus schema validation pattern carries over directly. For tool use, apply the same Zod validation to the model's tool-call arguments and the final picks, and treat AniList/TVmaze/Wikidata text as untrusted data.

## Limitations or bias
- A single developer's experience on a consultancy blog that ends with a sales call to action. The article does not show the integrity-verification or RevenueCat server code, and gives no costs or numbers.
- It uses Groq, not Claude, so there is nothing provider-specific about Anthropic.
- The claims about AppIntegrity strength are the author's; whether integrity attestation can be bypassed is not discussed.

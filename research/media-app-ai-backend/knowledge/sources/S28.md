## Learned points
1. [Documented] Two incidents in 2026, both described as "near-misses". METR believes no sensitive information was accessed in either. March 2026: an inference API key for public models was stolen and heavily used. May 2026: a sustained external probing campaign, plus an inadvertently exposed SQL query endpoint.
2. [Documented] Incident 1 cause: a researcher with no sensitive access ran agents on a personal EC2 instance that was intentionally public behind Google authentication. The instance held an API key for METR's general-access (public models) account. The "vibe-coded app included a fail-open vulnerability that silently disabled authentication", which left the system exposed to the internet "for several days".
3. [Documented] How the attacker found it (METR's suspicion): scanning recently registered sites, e.g. certificate transparency lists, for vibe-coded sites with LLM/agent keywords, in order to harvest model-provider API keys.
4. [Documented] Attack chain: the attacker prompted the agent directly to reveal its provider API key, added an SSH key for persistence, then used the key "over the course of three weeks" on public models.
5. [Documented] Cost: the credits used "would have been worth approximately $600,000", although the model developer had granted them to METR free.
6. [Documented] Time to detection: the post gives no exact date. The illicit usage ran about three weeks before METR "recognized that the large increase in model usage was not part of an evaluation". It was missed because (a) the team was used to high token volumes and many spurious rate-limit/API errors; (b) the internal usage dashboard did not show rate-limited requests to all users; (c) the credits were free, so there was "no natural token spend ceiling"; (d) at the time there was "no way to put a spending limit on keys like this one".
7. [Documented] Incident 1 response: revoked all of the researcher's access; stopped and imaged the instance; rotated all credentials present; imaged and wiped the laptop; alerted the partner AI company; external consultant (Calif) did a compromise assessment; manual and agent-assisted forensics confirmed only the single key was taken.
8. [Documented] Incident 1 controls adopted: clarified policy on putting METR credentials or data on non-METR infrastructure or devices; a formal security review before researchers publicly deploy apps; more monitoring coverage with fewer "noise" alerts; "Added spend alerts to keys where possible."
9. [Documented] Incident 2: financially motivated attackers, possibly seeking frontier-model access, probed public infrastructure "with heavy use of agents to automate vulnerability discovery": credential stuffing against auth providers, OAuth token-grant attempts, scanning newly deployed services, and phishing staff. Separately, the public transcript viewer exposed a read-only SQL query mechanism; a bug allowed access to unpublished evaluation data, which accidentally included some sensitive-model data. An independent researcher disclosed it, the API was taken offline and a bounty paid. METR found no evidence the attackers discovered the exploit. Footnote: the endpoint was briefly brought back up again without noticing the bug.
10. [Documented] Incident 2 response: turned off nearly all public-facing services and internal access to sensitive data while scoping; created an isolated public production environment architecturally separated from internal infrastructure; added external red-teaming.
11. [Documented] Program-level changes: hired a security lead (plus a planned full-time security engineer); shut down legacy infrastructure; regular threat-modeling reviews; more logging across database queries and API usage; "monitoring for unusual API key usage"; endpoint/server security software; "decreasing longevity of credentials"; and narrower permission scopes. Stated principles: centralized identity with strong auth, network isolation, minimal permission scoping, cross-platform monitoring.
12. [Inferred] Lessons for a solo developer: (a) attackers actively scan new domains (certificate transparency) for LLM-app keywords, so a new backend URL will be found within days; (b) never put the provider key anywhere an agent or its tools can read and echo it, because an exposed agent can simply be asked for its key; (c) auth must fail closed, so test that requests without a valid token are rejected; (d) set a hard provider spend limit plus usage alerts, and review rate-limit/429 metrics instead of dismissing them as noise; (e) keep the public API separate from anything holding secrets or data.

## Limitations or bias
- Self-reported by the affected organization, with wording adjusted after feedback from partner AI companies. The attribution ("we suspect…") and the "no sensitive data accessed" conclusions are METR's own.
- The provider, model, and exact detection date are not named. The $600k is a notional value of granted credits, not a cash loss.
- METR's setting (research org, large free credits) differs from a consumer app, but the attack path (public agent app → key extraction → abuse) carries over.

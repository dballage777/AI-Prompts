## Learned points
1. [Documented] Author byline is Dave Chismon (listed as "CTO for Architecture" in the "Written by" box; signed off as "David C, NCSC Technical Director for Platforms Research"). Thanks Johann Rehberger for discussions.
2. [Documented] Definition used: prompt injection is where developers concatenate their own instructions with untrusted content in one prompt and then treat the response as if there were a robust boundary between "what the app asked for" and the untrusted content. The term was coined in 2022.
3. [Documented] Core argument: in SQL, parameterised queries enforce a data/instruction separation so input can never be read as an instruction. Inside an LLM "there is only ever 'next token'", so prompt injection "may never be totally mitigated in the way that SQL injection attacks can be". Treating the two as equivalent is "dangerous" and undermines mitigations.
4. [Documented] Research approaches (detecting injection attempts, training models to prioritise instructions over data, marking what is data) are all described as "trying to overlay a concept of 'instruction' and 'data' on a technology that inherently does not distinguish between the two".
5. [Documented] Reframe: view the LLM as an "inherently confusable deputy". A classical confused deputy can be fixed; an LLM's risk cannot, so the goal is to reduce likelihood and impact. "If the system's security cannot tolerate the remaining risk, it may not be a good use case for LLMs."
6. [Documented] Recommendations are aligned to ETSI TS 104 223 (Baseline Cyber Security Requirements for AI Models and Systems) and grouped into four steps: developer and organisation awareness; secure design; make it harder; monitor.
7. [Documented] Awareness: security teams and risk owners must accept prompt injection "will remain a residual risk, and cannot be fully mitigated with a product or appliance".
8. [Documented] Secure design: when the LLM's output drives tools or APIs, impact becomes "whatever the worse case scenario would be of giving an attacker direct access to those tools/APIs". Protections should focus on deterministic (non-LLM) safeguards that constrain the system's actions. Cites Debenedetti et al. (2025, Google/ETH) and Beurer-Kellner et al. (2025; see S23).
9. [Documented] Privilege rule (from a Simon Willison / Baibhav Bista discussion): "when an LLM processes information from a party, the privileges it has drops to that of the party".
10. [Documented] Make it harder: Microsoft found marking data sections separately from instructions makes injection harder; even putting external content in XML tags can help. Be wary of deny-listing "known bad" phrases such as "ignore previous instructions", because there are infinite rephrasings.
11. [Documented] On vendors: "Beware any that claim they can 'stop' prompt injection, and instead look at those who understand how they reduce it."
12. [Documented] Monitor: log enough to spot suspicious activity, "potentially including full input and output of the LLM, as well as tool use, API calls etc."; detecting and responding to failed tool or API calls may reveal attackers honing an attack.
13. [Documented] Historical warning: SQL injection peaked around 2010 after a decade of breaches; the same wave may follow if genAI apps are not designed with prompt injection in mind.
14. [Inferred] For the media app: the model's read-only lookup tools should be limited to what any anonymous user could do anyway (the privilege-drop rule), so an injection in AniList/TVmaze/Wikidata text gains nothing beyond skewing a recommendation. Wrap tool results in clearly labelled tags, but do not rely on keyword filters. Log prompts, tool calls and failed tool calls server-side (mind privacy obligations when logging user text).

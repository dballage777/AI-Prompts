## Learned points
1. [Documented] The 2026 list order: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Excessive Agency, LLM04 Supply Chain, LLM05 Data and Model Poisoning, LLM06 Unbounded Consumption, LLM07 Misinformation, LLM08 Hidden Context Exposure, LLM09 Vector and Embedding Weaknesses, LLM10 Improper Output Handling. Canonical source is `2026/final/` in the GitHub repo.
2. [Documented] Definition: Unbounded Consumption is an LLM app allowing "excessive and uncontrolled inferences", which lets attackers disrupt availability, impose unsustainable financial costs, or steal IP through model cloning. The defining trait is cost asymmetry: the attacker triggers expensive compute at negligible cost to themselves, through crafted prompts, stolen credentials, or manipulated workflows.
3. [Documented] The entry says request-rate limiting alone "is no longer sufficient" because of extended-thinking models with large output budgets, multimodal inputs, agentic/tool-use protocols (MCP) that fan one request into many operations, and shared inference infrastructure. It calls for token-aware cost controls, hard spending caps, agent-level circuit breakers, and cost-attribution monitoring.
4. [Documented] Denial of Wallet (DoW) is listed both as a risk example (#2) and attack scenario (#4): a high volume of operations exploiting pay-per-use pricing, causing "unsustainable costs for the service provider" and risking "financial ruin".
5. [Documented] Nine risk examples: variable-length input flood and output explosion (including fine-tuning poisoning that breaks end-of-sequence so every output hits max length); DoW; large-context abuse (requests that stay just under the context limit while inflating per-request cost); reasoning-loop / thinking-token exhaustion via short benign-looking prompts that bypass input-size filters; adversarial inputs optimised for overconsumption (sponge examples); multimodal token inflation; model extraction/distillation theft (logit/logprob exposure speeds it up); agent-tool interactions flooding resources (recursive or infinite tool-calling loops, one call fanning out to hundreds); inference-infrastructure exploitation (vLLM, TensorRT-LLM, SGLang, Triton, Ollama).
6. [Documented] Prevention #1, rate limiting and input-size validation: per-source quotas, and move beyond requests/second to tokens-per-minute, tokens-per-day and estimated cost per request; use pre-flight token estimation to reject requests before inference begins.
7. [Documented] Prevention #2, hard spending caps: non-overridable budget ceilings per API key, user, team and cloud account that halt inference, "rather than alerting thresholds that fast-accumulating workloads can outpace". Caps should account for modality and tool-protocol cost differences.
8. [Documented] Prevention #9, agentic circuit breakers: enforce step limits, recursion-depth limits, time limits and per-run cost ceilings on all agent executions; use state hashing to detect recursive loops. Prevention #8: monitor agent-tool interactions for recursive sessions without a clear end state and baseline normal per-tool token consumption.
9. [Documented] Other prevention items: dynamic resource allocation per user/request (#3); sandbox the LLM's network/API reach (#4); graceful degradation under load (#5); limit queued and total actions plus scaling/load balancing (#6); scan inputs, especially images, for adversarial perturbations (#7); keep serving frameworks patched, disable unsafe deserialization, restrict special-token passthrough, authenticate all inference endpoints (#10).
10. [Documented] Scenario #8 (growing context in agentic sessions) gives numbers: per-turn cost climbs "from roughly $0.001 on the first turn to about $0.50 by turn 100" because each turn reprocesses the whole accumulated context; no single request trips rate limits, yet the aggregate across many concurrent or long sessions reaches "hundreds of dollars". The entry does not name the model or pricing behind those figures.
11. [Documented] Scenario #7: a malicious published tool (example given: "a Claude Skill on an open-source repository") instructs an agent to do recursive or high-fan-out tool calls, causing excessive token use for developers who adopt it.
12. [Documented] Scenario #5: functional model replication, using the API to generate synthetic training data to fine-tune an equivalent model.
13. [Inferred] For the media recommender: the backend proxy should enforce per-user token/cost quotas (not just request counts), cap `max_tokens` and any thinking budget server-side, cap the number of verification tool calls (AniList/TVmaze/Wikidata) per recommendation run, and cap conversation length or trim context so cost per session cannot grow without bound as in Scenario #8.
14. [Inferred] A per-day hard spending cap that actually stops calls (in the proxy, plus any provider-side spend limit) matters more for a solo developer than alerts, because the entry says alerting thresholds can be outpaced by fast-growing workloads.

## Limitations or bias
- Awareness document: gives categories and controls, not thresholds (no recommended token quotas, cap sizes or step limits).
- Scenario #8 dollar figures are illustrative; model and pricing are not stated.
- Small date mismatch: README says August 4, 2026; the OWASP site page shows August 3, 2026.
- Cited research (Gao et al., Li et al., Shumailov et al., Carlini et al.) was not opened here.

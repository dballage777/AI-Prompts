## Learned points
1. [Documented] Configuration in the wrangler config: a `ratelimits` array entry with `name` (binding name), `namespace_id` (a positive integer written as a string, unique in the account) and `simple: { limit, period }`. `simple` is the only supported type. Requires Wrangler 4.36.0 or later.
2. [Documented] `simple.period` "Must be either 10 or 60" seconds. No other window lengths are allowed, so the binding cannot express a daily or monthly quota.
3. [Documented] API: `const { success } = await env.MY_RATE_LIMITER.limit({ key, delta })`. `key` is any string; `delta` (default 1, positive integer) weights expensive operations (example: weight 10 for a search, 1 for a lookup). Local dev with `delta` needs Wrangler 4.157.0+; TypeScript needs `@cloudflare/workers-types` 5.20261106.1+.
4. [Documented] Decision rule: a call succeeds while the count is below the limit, even if its `delta` takes the count past the limit; a call that returns `success: false` does not add to the count.
5. [Documented] Locality: limits are per Cloudflare location. Requests in Sydney and in another location count separately even with the same namespace and key; "These counts do not combine into one worldwide limit."
6. [Documented] Accuracy: approximate and eventually consistent. Each check uses a locally cached count and updates sync in the background, so requests can exceed the configured limit, even within one location and one Worker. Example: with 30 per 10 seconds, a burst can produce more than 30 `success: true` results. Sharing a `namespace_id` across Workers shares counters but does not make the combined limit strict.
7. [Documented] For a strict limit across all locations, Cloudflare says to build a limiter with Durable Objects: route each credential's requests to the same object, check and update its counter together, persist it in durable storage, use one object per credential, and handle upstream HTTP 429s.
8. [Documented] Keying advice: use stable identifiers such as API keys, routes, user IDs or tenant IDs. IP addresses and locations are "not recommended" because many users share them, "especially on mobile networks or when using privacy-enabling proxies". Pattern: combine an actor ID with a resource or route ID. Multiple bindings can set different tiers (example: free 100/60s with namespace 1001, paid 1000/60s with namespace 1002).
9. [Documented] Monitoring: rate-limit bindings are not shown in the dashboard. Observe 429s with Workers Logs and Traces, or emit Analytics Engine data points when `success` is false.
10. [Documented] Durable Objects: each object has a globally unique name and attached storage that is "strongly consistent". Available on the Free plan (SQLite-backed only) and the Paid plan.
11. [Documented] DO pricing: Free plan gives 100,000 requests a day and 13,000 GB-s duration a day; exceeding fails with an error, and limits reset at 00:00 UTC. Paid plan gives 1 million requests a month, then $0.15 per million, and 400,000 GB-s, then $12.50 per million GB-s. Duration is billed at 128 MB regardless of real use. SQLite storage: Free plan 5 million rows read a day, 100,000 rows written a day, 5 GB total; Paid plan includes 25 billion reads a month (then $0.001 per million), 50 million writes a month (then $1.00 per million) and 5 GB-month (then $0.20 per GB-month). SQLite storage billing target date: January 7, 2026. Workers Paid has a $5 a month minimum. Cloudflare's example: one coordination DO with 1.5M requests a month comes to about $5.15 a month.
12. [Documented] Workers Paid ($5 a month minimum) includes 10 million requests a month; the Free plan allows 100,000 requests a day. Neither the rate-limit binding page nor the Workers pricing page lists a separate charge for the Rate Limiting binding (I searched both).
13. [Inferred] For a per-user Claude budget (for example N recommendation runs per day), the binding alone is unsuitable because of the 10- or 60-second windows and per-location counts. Use it as a cheap burst limiter (for example 5 calls per 60 seconds per user ID) and keep the daily or monthly quota in a Durable Object or database, keyed by verified user ID, never by IP.
14. [Inferred] Use `delta` to weight a full recommendation run (several Claude turns plus tool calls) more heavily than a single "explain this pick" call.

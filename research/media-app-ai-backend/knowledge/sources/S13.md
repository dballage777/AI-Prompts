## Learned points
1. [Documented] What it is: user profiles tell Anthropic which of your end customers each API request is for, so a safety enforcement action (restriction or ban) can apply to one end customer instead of your whole organization. Anthropic runs automated safety classifiers over API traffic; without a profile, "one end customer can trigger an enforcement action that applies to your whole organization."
2. [Documented] Flow: register each end customer once with `POST /v1/user_profiles` (normal API key, no Admin key needed), store the returned `uprof_...` ID on your customer record, then send it in the `anthropic-user-profile-id` request header on every request made for that customer. SDK argument `user_profile_id` (TS/Python), `userProfileId` (Java), CLI `--user-profile-id`.
3. [Documented] The header also works on token counting, Message Batches (applies to every request in the batch), and OpenAI-SDK-compatibility requests. On Amazon Bedrock (supported models only: Claude 4.7+, Sonnet 4.6, Haiku 4.5) it goes as a top-level `user_profile_id` body field instead; the Bedrock `Converse` API is unsupported.
4. [Documented] `access_type`: `application` (default) for an end customer who uses your product; `passthrough` (must be sent explicitly) for a company that buys API access from you. A company gets one profile, not one per employee.
5. [Documented] Don't create profiles for your own usage (a request with no profile ID counts as your own usage) — keep internal usage in a separate organization, because profiles belong to the organization, not a workspace. A workspace can have a profile attached via `user_profile_id` on Create/Update Workspace; then every inference request through it must carry that ID or is rejected.
6. [Documented] Fields (all optional): `name`, `metadata`, and in `external_user_details`: `entity_type`, `country`, `reference_id`, `onboarded_at`, `account_status`, `name_hash`, `email_hash`. Rules: omit unknown values (no placeholders; values in `external_user_details` can be replaced but never cleared — `null` is rejected with 400); send the customer's country, not yours; `reference_id` is your own stable ID (need not be unique).
7. [Documented] Privacy of identifiers: there is no email field; if you can't share a name or email, send `name_hash` / `email_hash` computed with a function you choose (consistent normalization across profiles so matches work). A profile holds only what you send plus Anthropic-set program/enforcement status — no conversation content. Anthropic uses the details for attribution, abuse monitoring, Usage Policy enforcement and trusted-access programs, and does not verify them. Processed under Anthropic's Privacy Policy.
8. [Documented] Validation: Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud and Anthropic-hosted Foundry check the ID on every request; malformed or another org's ID → 400 `invalid_request_error`. Batches check only format at creation; a wrong-org ID makes each batch request end `errored`. Google-managed Google Cloud and Bedrock only check format.
9. [Documented] `POST /v1/user_profiles` is NOT idempotent — every call creates a new profile even with the same `reference_id`. Create it once in onboarding; service instances should read the stored ID. No cap on profile count, but creation is rate-limited; contact the account team before bulk-registering an existing user base.
10. [Documented] Enforcement effects: profile responses include `enforcement_status` (`unrestricted` | `restricted` | `banned`) and `enforcement_actions` (each with `type` restriction/ban, `id` `enac_...`, `reason` one of `unsupported_region`, `fraud_or_abuse`, `high_harm`, `usage_policy_violation`, `account_compromise`, `unspecified`, plus `action`, `opened_at`, `expires_at`). While an action is open, Anthropic refuses some or all inference requests carrying that profile ID. Treat unknown values conservatively (unknown status → `restricted`).
11. [Documented] Monitoring: `GET /v1/user_profiles/{id}`; list with `enforcement_status[]=restricted&enforcement_status[]=banned`; or subscribe to Organization webhooks for open/close events. `updated_at` doesn't reliably change on enforcement changes. Don't send a `user-profiles-` value in `anthropic-beta` (old beta values like `user-profiles-2026-09-04` omit the enforcement fields). On Claude Platform on AWS enforcement fields are always unrestricted/empty.
12. [Documented] Update: `POST /v1/user_profiles/{id}` changes only sent fields; `metadata` merges key-by-key (empty string deletes a key). Delete: `DELETE /v1/user_profiles/{id}` removes your supplied data but not Anthropic's trust-and-safety records for that ID; requests with a deleted ID may still succeed for ~10 minutes, then get 400. For an erasure request from a continuing customer: create a new profile, switch, then delete the old one.
13. [Documented] Billing: profiles don't change billing or pricing on their own (Linked billing is a separate feature that uses them to identify who to bill).
14. [Documented] `metadata.user_id` guidance: the page does NOT describe it as legacy. It says that within a company profile, if a request comes from one identifiable person, also set `metadata.user_id` on the Messages request (the request's own `metadata` object, not the profile's `metadata`) to an identifier for that person; optional, "helps Anthropic detect misuse by one person."
15. [Documented] Eligibility framing: the page targets anyone who operates "a platform or gateway, or resell[s] API access", and the `application` access type covers end customers who use your product. Available where `/v1/user_profiles` exists: Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud (not Google-managed Google Cloud, Bedrock or Foundry, which must create profiles in a Claude API/AWS-platform org). No paid-tier or approval requirement is stated.
16. [Inferred] For the consumer media app: each app user is an end customer of your product → create one `application` profile per user at sign-up (server-side, once), store the `uprof_` ID with the user row, and have the proxy add `anthropic-user-profile-id` on every Claude call. This contains the blast radius if one user tries prompt-injection or abusive content — enforcement can hit that profile rather than suspend the whole app. Send only hashed email (`email_hash`) and `country`/`reference_id`; avoid real names for minors/privacy. Poll or webhook `enforcement_status` and block restricted/banned users in your own backend before calling the API.
17. [Inferred] Keep your own testing/dev traffic in a separate organization (not just a workspace) so it isn't mixed with end-customer traffic, as the page recommends.

## Limitations or bias
- Vendor docs. The page frames profiles mainly for platforms/gateways/resellers; whether per-individual profiles for a consumer app with many users is the intended granularity is implied by `application` but not stated with a consumer example. Profile-creation rate limits are unpublished. Field length limits are on the API reference page (not read).

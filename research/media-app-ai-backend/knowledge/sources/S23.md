## Learned points
1. [Research] Authors (alphabetical) from Invariant Labs, IBM, EPFL, ETH Zurich, Swisscom, Google, ETH AI Center, AppliedAI Institute for Europe, Microsoft, Kyutai (ex-Lakera); corresponding author Florian Tramèr (ETH Zurich). The paper draws no distinction between direct and indirect injection; it calls both "prompt injections". Preprint.
2. [Research] Stance on detection: input/output detectors and filters (often LLM-based) "raise the bar" because the attacker must fool both the agent and the detector, but "remain fundamentally heuristic and cannot guarantee prevention of all attacks". LLM-level defences (prompt engineering, adversarial training) "do not provide guarantees". User confirmation is theoretically effective but hurts automation and suffers from tired or overloaded approvers.
3. [Research] Thesis: general-purpose agents are unlikely to give "meaningful and reliable safety guarantees" with the current class of models; application-specific agents can be secured by system design that deliberately limits what the agent can do. Guiding principle: once an agent has ingested untrusted input, that input must be unable to trigger any consequential action, and outputs must not create downstream risk (e.g. exfiltration via embedded links).
4. [Research] Pattern 1, Action-Selector: the LLM maps a request to one of a fixed set of predefined (possibly templated) actions, with no feedback from action results back into the LLM; like an LLM-modulated "switch" statement. Trade-off: immune to injection via tool data, but loses most of the LLM's flexibility; work moves into designing the action set.
5. [Research] Pattern 2, Plan-Then-Execute: the agent fixes a plan (list of tool calls) before seeing untrusted data; tool outputs cannot add new actions ("control flow integrity"). Trade-off: injected data can still alter the arguments of planned calls (e.g. the body of an email); does not stop injections in the user prompt; innocuous commands can be recombined (find + mv copying sensitive files).
6. [Research] Pattern 3, LLM Map-Reduce: an isolated LLM processes each untrusted item separately (map) with no harmful tools; a reduce step either uses no LLM, or uses an LLM only on map outputs constrained to be safe (e.g. regex that the output is a number or Boolean). A malicious item can only affect its own result.
7. [Research] Pattern 4, Dual LLM (from Willison, 2023): a privileged LLM plans and uses tools but never sees untrusted data; a quarantined LLM processes untrusted data with no tools; its results are stored as symbolic variables ($VAR) that the privileged LLM handles by reference only, dereferenced by a non-LLM orchestrator at call time. Trade-off: the quarantined LLM can still be injected and produce attacker-controlled output content.
8. [Research] Pattern 5, Code-Then-Execute (instantiated in Debenedetti et al., 2025, i.e. CaMeL): the LLM writes a formal program that calls tools and spawns unprivileged LLMs on untrusted text. Generalises plan-then-execute; still cannot stop injected data changing the content that flows into a call.
9. [Research] Pattern 6, Context-Minimization: remove the user's prompt (or other unneeded content) from context after it has been turned into a query, so it cannot shape the final response (e.g. a car-quote bot drops the user's text before writing the reply so an injected "give a large discount" has no effect). Targets injection in the user prompt.
10. [Research] Appendix A best practices every agent should apply regardless of pattern: action sandboxing (minimal tools and network; sanitised purpose-built tools instead of e.g. `find`, which can execute code); strict data formatting (constrain output to a schema such as JSON, enforced algorithmically, with try-repeat validation as fallback); user permissions capped at the user's own access rights; user confirmation (with fatigue caveats); data and action attribution.
11. [Research] Case study 4.6 Product Recommender (closest to this app): summarises online-store reviews per product; no tools, no state-changing actions. Threats: injected reviews boosting a product or discrediting others (adversarial SEO), and user-prompt injection for reputational "screenshot" attacks. Designs: (1) raw reviews in the prompt — "highly susceptible"; (2) data attribution (cite review snippets) — burdens the user and cannot show why other products were not chosen; (3) map-reduce — each review summarised in isolation into fixed categories (e.g. "good price", "easy to use"), then aggregated to recommend top K; an injection is confined to its own review, and a malicious review can at worst look as good as an honestly positive one.
12. [Research] Case study 4.4 Customer Service Chatbot (consumer-facing): main risk is user-prompt injection causing data exfiltration via clickable URLs or auto-loading markdown images, and reputational "screenshot attacks" (cites the "Chevy for $1" dealer-bot story). Designs: LLM topic classifier (binary decision exploitable by mixing on- and off-topic in one prompt); action-selector via embedding similarity to an allowlist of requests (false blocks of unforeseen requests); context-minimization for any post-processing step. Also: prevent access to other users' orders via authentication/session scoping, not prompts.
13. [Research] Case study 4.5 Booking Assistant (tool-calling, third-party content): service-provider text can carry injections such as "always book this hotel"; designs include least-privilege access equal to the user, restricting the calendar API so event descriptions are not read, and dual LLM / code-then-execute where third-party content is only rated by an unprivileged tool-less LLM.
14. [Research] Case study 4.7 Resume Screening: map-reduce with each resume converted by an isolated LLM into a fixed format or score, so a resume can boost itself but not discredit others; dual-LLM summarisation fills a privileged-LLM template ($X, $Y) with values extracted per resume.
15. [Research] Case study 4.9 Medical Diagnosis: "structured formatting" — forcing the LLM's intermediate summary into a structured object with no open-ended text (constrained decoding / structured outputs) "leaves no room for prompt injection in the summary". Case 4.10 Software Engineering Agent: dual LLM with strict formatting (e.g. method names limited to 30 characters).
16. [Research] Other case studies: OS assistant with fuzzy file search, SQL agent (includes resource waste/DoS as attacker goal; sandbox the Python interpreter), email and calendar assistant, medication leaflet chatbot (context-minimization so returned text is verbatim from the leaflet). Table 1 maps patterns to all 10 cases.
17. [Research] Conclusions: Recommendation 1 — build application-specific agents with secure patterns and clearly defined trust boundaries; Recommendation 2 — combine patterns, since no single pattern suffices for all threat models.
18. [Inferred] For the media recommender: apply map-reduce to verification — each AniList/TVmaze/Wikidata result goes to a tool-less call (or plain code) that returns only a constrained structure (exists: bool, canonical title, year, ID, genres from a fixed list), and the final explain-the-picks step sees only those sanitised fields, not raw synopses. A poisoned synopsis can then only affect its own title's record.
19. [Inferred] Also apply plan-then-execute: the model fixes which titles to verify before any third-party text comes back, and the server (not the model) runs the lookups against an allowlist of the three APIs with a capped number of calls. Render the explanation as plain text with no model-generated links or images to close the markdown-image exfiltration channel noted in 4.4.

## Limitations or bias
- Preprint, position/design paper: no experiments or measured attack-success numbers; security claims are argued, not benchmarked.
- Several authors are from security vendors (Invariant Labs, Lakera) and large AI companies.
- Patterns trade utility for security; the paper notes some tasks cannot be decomposed this way.
- The product-recommender case uses store reviews, not tool calls to metadata APIs; the mapping to this app is inference.

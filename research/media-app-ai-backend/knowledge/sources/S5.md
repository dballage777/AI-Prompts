## Learned points
1. [Documented] Streaming is enabled with `"stream": true` on the Messages API and uses server-sent events (SSE). Each event has an SSE event name (e.g. `event: message_stop`) and a matching `type` field in its JSON data. Streaming is "available on every model".
2. [Documented] Event order: `message_start` (a `Message` with empty `content`) → for each content block: `content_block_start`, any number of `content_block_delta`, `content_block_stop` (each with an `index` matching its position in the final `content` array) → one or more `message_delta` (top-level changes such as `stop_reason`, `usage`) → a final `message_stop`. Some blocks arrive whole with no deltas: `redacted_thinking`, server tool results such as `web_search_tool_result`, and `fallback` blocks at a server-side fallback model boundary.
3. [Documented] Token counts in the `usage` field of `message_delta` are *cumulative* (warning on page). `message_start` carries initial `usage` (e.g. `input_tokens`, `output_tokens: 1`); the final `message_delta` carries the output total (and, with server tools, `server_tool_use.web_search_requests`).
4. [Documented] Streams "might also include any number of `ping` events" (`event: ping`, `data: {"type": "ping"}`), dispersed anywhere in the stream.
5. [Documented] Errors can arrive mid-stream as an `error` event, e.g. `{"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}`, which "would normally correspond to an HTTP 529 in a non-streaming context". With the SDK, your code does not receive this event; the SDK ends the stream and the reading code gets an error instead.
6. [Documented] (handle-errors) Once a stream starts the API has already returned HTTP 200, so the SDK does NOT retry a mid-stream error. In TypeScript every error event surfaces as `Anthropic.APIError` whose HTTP status is 200 or missing, so a branch on status code or on a code-specific class will not catch it; check `err.type === "overloaded_error"` (and read `err.apiMessage`).
7. [Documented] New event types may be added under the versioning policy; code "should handle unknown event types gracefully".
8. [Documented] Delta types: `text_delta` (`text`), `input_json_delta` (`partial_json` — partial JSON strings for `tool_use.input`; accumulate and parse at `content_block_stop`, final `input` is always an object), `thinking_delta`, and `signature_delta` (sent just before `content_block_stop` of a thinking block). By default the API buffers each tool-input key/value until complete, so there can be pauses during tool use; per-tool `eager_input_streaming` enables fine-grained tool streaming.
9. [Documented] SDK helpers: TypeScript `client.messages.stream({...}).on("text", ...)`; `await stream.finalMessage()` accumulates all events into the same `Message` object that `messages.create()` returns. The Python and TypeScript helpers also expose parsed tool `input` incrementally.
10. [Documented] When streaming is effectively required: getting the final message via streaming "is especially useful for requests with large `max_tokens` values, where the SDK requires streaming to avoid HTTP timeouts" (the docs example uses `max_tokens: 128000` with `.stream()` + `finalMessage()`).
11. [Documented] Error recovery, Claude 4.5 and earlier: capture the partial response, send a continuation request with the partial text as the start of a new assistant message, resume streaming. Claude 4.6 and later: instead add a *user* message containing the partial response and an instruction to continue (sample: "Your previous response was interrupted and ended with [previous_response]. Continue from where you left off."). Tool use and thinking blocks cannot be partially recovered; resume from the most recent text block.
12. [Documented] (streaming refusals) On Claude 4 and later, when streaming classifiers intervene the stream ends with `stop_reason: "refusal"`; `stop_details` (`type: "refusal"`, `category`, `explanation`) arrives on the `message_delta` event. Partial text already streamed stays in `content` (example shows `"text": "Hello.."`). `category` and `explanation` can be `null`; branch on `stop_reason` or `stop_details.type` and supply your own user-facing message.
13. [Documented] After a refusal you "must reset the conversation context before continuing" (remove/rephrase the triggering turn or clear history); otherwise continued refusals. Re-sending to the same model usually refuses again; alternatives are server-side fallback, SDK middleware, or a manual retry on another model (redeem "fallback credit" so prompt-cache cost is not paid twice). Claude Haiku 5.5 has no server-side fallback and its refusals carry no fallback credit, so its retry must be set up client-side.
14. [Documented] Refusals are HTTP 200 responses, not errors: error-rate monitoring will not surface them; track refusals as their own signal. Usage metrics are still provided; whether a refusal is billed depends on timing and category. In Message Batches a refusal is a "succeeded" result with `stop_reason: "refusal"`. `reasoning_extraction` refusals are an exception: change the prompt rather than retry elsewhere.
15. [Inferred] For the app: the backend should consume the Anthropic stream with the TS SDK and relay only text deltas (plus its own status events) to the phone; it must handle (a) a thrown `APIError` with `type: "overloaded_error"` mid-stream (no auto-retry — the server decides whether to retry or resume), (b) `stop_reason: "refusal"` on `message_delta` (discard or mark partial text already shown, reset context, show a friendly message), and (c) unknown event types. Because partial text may already be on screen when a refusal or error arrives, the client UI needs a "retract/replace" state.

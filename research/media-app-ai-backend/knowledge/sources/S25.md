## Learned points
1. [Documented] `@upstash/ratelimit` is described as "the only connectionless (HTTP based) rate limiting library", aimed at serverless runtimes, Cloudflare Workers, Vercel Edge and Deno. Its examples include "Rate limit your Chatbot" (an endpoint that streams LLM output).
2. [Documented] Fixed window (`Ratelimit.fixedWindow(10, "10 s")`): very cheap; newer requests are not starved by past bursts. Cons: bursts at window boundaries leak through, and a "stampede" can occur when a new window begins. Resets fall on fixed time boundaries, not on the first request.
3. [Documented] Sliding window (`Ratelimit.slidingWindow(10, "10 s")`): weights the previous window, for example `4 * ((60 - 15) / 60) + 5 = 8`. This fixes the boundary problem but costs more storage and compute, and it is "only an approximation" that assumes uniform flow. Its `reset` value is the start of the next window, not an exact time.
4. [Documented] Token bucket (`Ratelimit.tokenBucket(5, "10 s", 10)`, meaning refill 5 tokens every 10 s up to a maximum of 10): smooths bursts and allows a larger initial burst (maxTokens > refillRate), but is "Expensive in terms of computation". Not supported by `MultiRegionRatelimit`.
5. [Documented] Redis commands per `limit()` call. Fixed window: 3 on first use (EVAL, INCR, PEXPIRE), then 2. Sliding window: 5 on first use, then 4, and 3 when rate-limited on a cache miss. Token bucket: 4, and 2 when rate-limited. A blocked identifier found in the in-memory cache costs 0. Add 1 per call for analytics (ZINCRBY), 1 for dynamic limits, and 2 for deny lists. The auto IP deny list costs 9 commands a day.
6. [Documented] `ephemeralCache` (a `Map` created outside the handler) is on by default. It stores only blocked identifiers with their unblock timestamp, so repeat offenders are rejected without a Redis call. In serverless it is often empty after cold starts.
7. [Documented] `timeout` (default 5 seconds): if Redis does not answer in time, the request is allowed (fail-open), and `reason` shows the timeout.
8. [Documented] Multi-region: `MultiRegionRatelimit` checks the closest database, returns immediately, then replicates asynchronously with CRDTs; "there is no way to guarantee the set ratelimit is not exceeded by a small margin". On Cloudflare Workers or Vercel Edge you must `context.waitUntil(pending)`. Sliding window in multi-region "results in large number of commands"; fixed window is recommended there. Dynamic limits are single-region only.
9. [Documented] Other features: multiple limits (free and paid tiers), custom rates (consume more than 1 token, for example by request size), deny lists (user agent, country, IP), and an analytics dashboard.
10. [Documented] Redis pricing (as shown 2026-11-25): Free $0 with 500K commands a month, 250 MB data, 1 database, 10 GB bandwidth a month, 10,000 commands a second max. Pay as you go: $0.2 per 100K commands, $0.25 per GB storage, first 200 GB bandwidth a month free then $0.03 per GB, optional monthly budget cap with emails at 70% and 90%. Fixed plans start at $10 a month (+$5 per read region) with no per-command billing. On Global databases, writes replicate to each read region and each copy counts as a command (100K writes with one read region = $0.40). Paid databases do not get the free 500K.
11. [Inferred] Rough cost for this app: fixed window at about 2 commands per check means 500K free commands cover about 250K rate-limit checks a month. On pay as you go, 1M checks cost about 2M commands, or $4. That is negligible next to Claude token costs. Turning on analytics adds about 50%.
12. [Inferred] Token bucket fits a "N recommendation runs, refilling over time" per-user quota. Key it by the verified user ID from the backend's auth step, and use `rate` (custom cost) to charge a full multi-tool run more than a follow-up. Single-region is fine for a solo app, and avoids the multi-region overshoot and the `waitUntil` requirement.
13. [Inferred] The default fail-open timeout means a Redis outage removes the cost guard. For a paid LLM call, consider a shorter timeout plus fail-closed handling (check `reason`), or a provider-side spend cap as a backstop.

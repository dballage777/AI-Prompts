## Learned points
1. [Documented] Definition: prompt injection is any input (direct user input, retrieved content, tool output, image/audio/video, intermediate reasoning, persistent memory) that alters model behaviour in ways the developer did not intend. LLMs make no architectural distinction between instructions and data, "so there is no clean equivalent to parameterized queries (NCSC, 2025)".
2. [Documented] Three deployment properties worsen it: context-window pooling (system prompt, user input, tool outputs, memory are one token stream with no enforced trust boundary); memory persistence (an injection written to memory/RAG taints later sessions); agentic execution (tool outputs re-enter context; blast radius becomes whatever the tools can reach).
3. [Documented] Threat-model axes: delivery surface (direct, retrieved, tool output, tool connection channel, memory); propagation (single-shot, multi-step, cross-session, self-replicating); encoding (plain text, base64/obfuscation, invisible Unicode, multimodal/steganographic, low-resource language).
4. [Documented] Direct injection: user (or someone with the user's access path) supplies the input; can be intentional (jailbreak) or unintentional (pasted content containing instructions). Jailbreaking is the subset aimed at violating safety protocols.
5. [Documented] Indirect injection: model ingests external content (web page, email, tool response, RAG passage, MCP output, database row...) containing instructions the user never saw. Surfaces are tiered: untrusted (public web, unknown email, search results), semi-trusted (bug-tracker issue titles, package READMEs, "third-party API responses"), trusted (developer's own repos/databases, which may still be seeded via a public form).
6. [Documented] Core stance: "no reliable prevention mechanism exists today" (consistent with NIST 2025, NCSC 2025, Debenedetti et al. 2025), so defence is architectural: assume the instruction boundary will be bypassed and constrain what the model can do and where its output can go. Cites Willison's "lethal trifecta" (private data + untrusted content + external communication; remove one leg).
7. [Documented] Mitigations 1–4: declarative role/capability limits in the system prompt (partial only); strict output schema validated in trusted application code, "using structural validation rather than a second LLM call" (catches format violations, not semantic manipulation); filter at every modality boundary; hold credentials and state-change capability in application code, least privilege per operation, privileged calls through a deterministic policy engine.
8. [Documented] Mitigation 5: strip tag-block (U+E0000–E007F), variation-selector (U+FE00–FE0F) and zero-width (U+200B, U+200C, U+200D, U+2060) characters at every ingest and render boundary. Does not stop visible-text payloads.
9. [Documented] Mitigations 6–8: pass external content through a separate, provenance-labelled channel (helps only against non-adaptive attackers; StruQ was bypassed adaptively); human confirmation for privileged/irreversible/externally visible actions showing the exact rendered action; Meta's "Rule of Two" as a floor: an agent with (A) untrusted input, (B) sensitive data and (C) state change/external communication needs per-action human approval, and [A,B] or [A,C] need a residual-risk assessment.
10. [Documented] Mitigations 9–11: treat memory writes as privileged; pin/sign/verify MCP servers and tool packages and audit tool descriptions; test against adaptive attackers — Nasr et al. (2025) found static attack success near zero but adaptive success above 90% for most of 12 recent defences.
11. [Documented] Scenarios relevant to a recommender: #2, a summarised web page makes the model emit a markdown image whose URL exfiltrates the conversation; #4, RAG poisoning with as few as five poisoned documents reaching about 90% attack success over millions of texts (W. Zou et al., 2025); #5, payload split across fields to evade per-field classifiers, manipulating a recommendation.
12. [Documented] Other scenarios: #7 zero-click email exfiltration against Microsoft 365 Copilot bypassing its injection classifier and link-redaction filter; #8 Amazon Q destructive-prompt commit and runtime code execution (July 2025); #9 MCP trusted-backend injection (poisoned GitHub issue exfiltrating private repos; Supabase MCP running `service_role` dumping a production DB; malicious `postmark-mcp` package BCC'ing email across an estimated 300 organizations).
13. [Documented] LLM08 Hidden Context Exposure: assume the system prompt, tool schemas and other hidden context are discoverable; never put credentials, connection strings or tokens there, and never rely on hidden-context secrecy for authorization, privilege separation, policy enforcement or content filtering. Severity ranges informational → medium → high (embedded credentials, or reliance on secrecy) → critical (chains to RCE or broad exfiltration).
14. [Documented] LLM08 mitigations: keep sensitive data out of hidden context; enforce critical behaviour with deterministic systems outside the model (harmful-content detection by external safeguards, not prompt text); enforce authorization independently of the LLM. Scenario #2: probing extracts tool list and parameter schemas to target later injections.
15. [Inferred] For the media app: AniList/TVmaze/Wikidata responses are "semi-trusted" third-party API responses, i.e. indirect-injection surfaces (user-editable descriptions, synopses, wiki text). Strip invisible Unicode from tool results, validate the model's final recommendation JSON in server code, and do not render model-produced markdown images or arbitrary links in the app.
16. [Inferred] The recommender's tools are read-only and it holds no other users' data, so per the Rule of Two it lacks leg (C) and mostly (B); the main residual risks are output manipulation (pushing a title), reputational "say something off-topic" output, and cost abuse. Keep it that way: no write tools, no API keys or secrets in the system prompt, and treat the system prompt as public.

## Limitations or bias
- Awareness document summarising cited research and incidents; the primary papers and incident reports were not opened here, so the numbers (90% adaptive success, five-document RAG poisoning, 300 organizations) are OWASP's reporting of those works.
- Mostly framed around high-agency agents (email, shell, MCP); less direct guidance for low-agency read-only recommenders.

## Summary-only items
- None (both entries read in full).

## Best used for
- Classifying the app's injection surfaces (direct vs. indirect via third-party API text), choosing architectural controls (output schema validation in code, least privilege, Unicode stripping, no secrets in prompts), and citing the 2026 OWASP position that prompt injection cannot be reliably prevented.

- Type: blog (expert practitioner; he coined the term "prompt injection")

## Learned points
1. [Documented] The framework: an agent is exploitable when it combines (1) access to private data, (2) exposure to untrusted content (any way attacker-controlled text or images can reach the LLM), and (3) the ability to communicate externally in a way that can exfiltrate data. If it has all three, "an attacker can easily trick it" into reading private data and sending it to the attacker.
2. [Documented] Root cause: LLMs follow instructions found in content, whatever its source. Everything is joined into one token sequence, so models "are unable to reliably distinguish the importance of instructions based on where they came from." Summarizing a web page, reading an email, processing a document or looking at an image can all carry instructions.
3. [Documented] Telling the model in your own prompt not to obey such instructions reduces the risk but cannot be relied on, because outputs are non-deterministic and malicious instructions can be phrased in endless ways.
4. [Reported] Listed real exploits (most fixed promptly by the vendors, usually by closing the exfiltration channel): Microsoft 365 Copilot, GitHub's official MCP server and GitLab Duo (weeks before June 2025), and earlier ChatGPT (Apr 2023), ChatGPT Plugins, Google Bard, Writer.com, Amazon Q, Google NotebookLM, GitHub Copilot Chat, Google AI Studio, Microsoft Copilot, Slack, Mistral Le Chat, xAI Grok, Anthropic's Claude iOS app (Dec 2024) and ChatGPT Operator (Feb 2025).
5. [Documented] Exfiltration channels are "almost limitless": any tool that can make an HTTP request, whether to an API, to load an image, or "even providing a link for a user to click", can carry stolen data out.
6. [Documented] MCP makes the risk easy to create, because users mix tools from different sources. One tool can supply all three legs: the GitHub MCP exploit read attacker-filed public issues, accessed private repos, and opened a PR that exfiltrated the data.
7. [Documented] Guardrail products that claim to catch "95% of attacks" are not enough: "in web application security 95% is very much a failing grade." There is no known 100% reliable prevention.
8. [Documented] For application developers he points to design patterns (the "Design Patterns for Securing LLM Agents against Prompt Injections" paper's six patterns; Google DeepMind's CaMeL). Core principle quoted from that paper: once untrusted input is ingested, the agent "must be constrained so that it is impossible for that input to trigger any consequential actions." For end users mixing tools, the only safe option is to avoid the trifecta entirely.
9. [Documented] Terminology: prompt injection (mixing trusted and untrusted content, named after SQL injection) is distinct from jailbreaking (tricking the model into saying embarrassing things). Developers who conflate them wrongly dismiss prompt injection as irrelevant.
10. [Inferred] For the media recommender: AniList/TVmaze/Wikidata responses are leg 2 (untrusted content: synopses, user-editable wiki text). The user's taste profile and any account data are leg 1, a mild version. Leg 3 includes any tool that fetches URLs chosen by the model, any rendered Markdown images or links in the app, and any write action. Removing leg 3 is the most reliable control: make tools read-only with fixed hosts and server-built URLs; render the model's output as plain text or allow-listed links only (no remote images from model-chosen URLs); expose no tools that send messages or write data.
11. [Inferred] Treat tool results as data. Server code should validate that each verified title matches a structured API record (ID, title, year) rather than trusting free text the model relays, so injected text in a synopsis cannot change which titles are shown.

## Limitations or bias
- Opinion and synthesis blog post, not a measured study. The exploit list links out to individual write-ups that were not opened here.
- Written June 2025. The page's series list shows later posts (e.g. "Agents Rule of Two", Nov 2025) that may refine the framework; those were not read.
- The post focuses on data exfiltration. Other harms, such as cost abuse, misleading output, or unwanted actions without exfiltration, are only implied.

## Summary-only items
- The "Design Patterns" and CaMeL papers are mentioned only through this post's one-line description, not read.

## Best used for
- A simple threat-model lens for the app's tool-use loop: list which of the three legs exist and remove one (ideally external communication). Also useful for the argument that prompt-based defenses and guardrail products are not enough.

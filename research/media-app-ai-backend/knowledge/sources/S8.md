## Learned points
1. [Documented] Workspaces separate projects, environments or teams inside one organization with centralized billing. Every org has a Default Workspace (cannot be renamed, archived or deleted). IDs use the `wrkspc_` prefix. Max 1,000 workspaces per org by default (archived and Default don't count); over the limit → 400 "Workspace limit reached".
2. [Documented] Per-workspace spend limits: set monthly spend limit at platform.claude.com/settings/spend-limits → Workspace limits → choose workspace → Set/Adjust limit. If Anthropic bills you directly, you can add email notifications when spending reaches an amount you choose ("Add notification" / "Edit" next to Email notifications).
3. [Documented] Per-workspace rate limits: RPM, ITPM, OTPM per model, set at platform.claude.com/usage/limits → Workspace dropdown → Edit next to a model; also programmatically via the Rate Limits API (which stores values above the org limit but enforces the lower of the two).
4. [Documented] Workspace limits can only lower, never raise, org limits; unset workspace limits equal the org's; org-wide limits always apply even if workspace limits sum to more. Reaching a workspace spend limit returns 400 `invalid_request_error` "You have reached your specified workspace API usage limits" (S3).
5. [Documented] Caveat: a spend limit on the Default Workspace may not count or stop some usage (Console playground, Managed Agents sessions, Claude Code/Claude Desktop via Console sign-in); the org spend limit covers all of it. Default-workspace spend limits are unavailable on Claude Platform on AWS and Anthropic-managed Google Cloud.
6. [Documented] Key scoping: every non-admin request runs in exactly one workspace and can only access that workspace's resources. A workspace key (legacy, ownerless) always runs in its workspace. Personal or service-account keys either are scoped to a single workspace, or are unscoped and choose the workspace per request via the `anthropic-workspace-id` request header (account must have access).
7. [Documented] Workspace-scoped resources: Files (Files API), Message Batches, Skills; prompt caches are isolated per workspace on the Claude API (S1).
8. [Documented] Response header `anthropic-workspace-id` carries the `wrkspc_` ID the key resolved to (absent on Admin API requests and pre-auth failures like 401); use it to confirm which workspace's usage, cost and rate limits a request counted against.
9. [Documented] Roles: Workspace User (playground only), Workspace Limited Developer, Workspace Developer (create/manage keys, use API), Workspace Admin, Workspace Billing (inherited only). Org admins get Workspace Admin everywhere.
10. [Documented] Archiving a workspace archives all its API keys within seconds and cannot be undone. Personal/service-account keys stop working shortly after their account is removed from the workspace; service-account keys survive removal of the human who created them; legacy workspace keys keep working.
11. [Documented] Admin API (workspaces, members) needs an Admin API key, an `org:admin` OAuth token, or an unscoped personal/service-account key; workspace-scoped keys don't work there.
12. [Documented] Usage and cost per workspace via the Usage and Cost Analytics API (Default Workspace reported under its real ID; legacy Usage and Cost API shows `null`).
13. [Documented] Suggested pattern: separate Development / Staging / Production workspaces, with lower rate limits for development.
14. [Documented] A Claude Code workspace is auto-created when a member signs into Claude Code with a Console account; it is rate-limited separately and is the only workspace supporting per-user monthly spend limits.
15. [Inferred] For the solo developer: put the production app's server key in a dedicated "Production" workspace with its own spend limit and email alert set below the tier cap, and keep dev/testing in a separate workspace with tighter limits — a runaway dev loop or a leaked dev key can't drain production budget. Note prompt caches don't cross workspaces, so don't split production traffic across workspaces needlessly.
16. [Inferred] Workspace spend limits are monthly and org/workspace-wide, not per end user; per-user quotas still have to be enforced in your own backend.

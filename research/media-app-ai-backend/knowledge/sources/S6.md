## Learned points
1. [Documented] Framing: an API key is "a digital key to your account"; like a credit card number, whoever obtains it "incur[s] charges on your behalf". The most frequent leak cause cited is accidental exposure in public code repositories or third-party tools (committing plaintext keys to public GitHub repos).
2. [Documented] Rule 1, never share: keep keys confidential; others should get their own key; do not put keys in public forums, emails, or support tickets "even between you and Anthropic"; uploading a key to a third-party tool (web IDE, cloud provider, CI/CD) gives that tool's developer access to your Console account; with third-party providers always add the key "as an encrypted secret" and never directly in code or configuration files.
3. [Documented] Rule 2, monitor: regularly review the Logs page (platform.claude.com/logs) and Usage page (platform.claude.com/usage). Custom-rate-limit orgs: set spend limits (platform.claude.com/settings/billing) and workspace rate limits (platform.claude.com/usage/limits) as a safeguard against leaked keys or errant scripts. Standard-rate-limit orgs: configure auto-reload on the Billing page and "carefully consider auto-reload limits", which also act as a safeguard against runaway usage.
4. [Documented] Rule 3, environment variables and secrets: inject the key via environment variables; in cloud deployments use the provider's secret management to pass it as an env var. If using dotenv locally, add `.env` to `.gitignore`. "In cloud environments, prefer encypted secret storage instead of dotenv files." Example variable name: `ANTHROPIC_API_KEY`.
5. [Documented] Rule 4, rotate: rotate "on a consistent schedule (for example, every 90 days)" by creating new keys and deactivating old ones.
6. [Documented] Rule 5, separate keys per purpose: different keys for development, testing and production so usage can be correlated and a compromised use case disabled alone.
7. [Documented] Rule 6, secret scanning: enable your source-control provider's secret scanning; use SAST tools such as Gitleaks; integrate scanning into CI/CD to catch secrets before they reach the main branch.
8. [Documented] Rule 7, use a Key Management System as secrets multiply: centralized encrypted storage, fine-grained access control, audit trails, easy rotation, integrations.
9. [Documented] GitHub Secret scanning partner program: GitHub scans public repositories for exposed Claude API keys and notifies Anthropic; Anthropic "automatically deactivates the exposed API key"; the affected user receives a detailed email.
10. [Documented] If compromise is suspected: revoke immediately in Console > API keys (platform.claude.com/settings/keys) > three-dot menu > "Delete API key".
11. [Documented] The article itself does not state "never put the key in client/mobile app code" in those words; that statement comes from the TypeScript SDK docs (S11), which link to this article as the reason browser use is disabled by default.
12. [Inferred] For the app: the Anthropic key lives only on the backend (host secret store, not a committed `.env`, not an Expo `EXPO_PUBLIC_*` variable, which is bundled into the app). Use a separate production key/workspace with a spend limit or capped auto-reload, rotate about every 90 days, run Gitleaks in CI, and keep the repo scanned — an auto-deactivated leaked key would also take the live app down until replaced.

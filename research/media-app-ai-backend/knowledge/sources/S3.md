## Learned points
1. [Documented] Two kinds of limits: spend limits (max monthly cost per organization) and rate limits (requests/tokens per period). Both enforced at the organization level; you can set lower per-workspace limits. Limits are maximums, not guaranteed minimums.
2. [Documented] Tiers are now named Start, Build, Scale, and Custom. Organizations are placed automatically "based on usage history and account standing" and move up over time. New/low-history organizations may start in an "Evaluation tier" with limits below the standard tables, which rise automatically as history builds (an anti-fraud measure). The page lists NO deposit/credit-purchase thresholds for tiers (the older deposit-based tier scheme is not described).
3. [Documented] Monthly spend cap per tier: Start $500; Build $1,000; Scale $200,000; Custom = no cap (arranged with account team). See your tier at platform.claude.com/usage/limits; set your own lower org spend limit at platform.claude.com/settings/spend-limits.
4. [Documented] Reaching the tier spend cap: usage pauses until 00:00 UTC on the 1st of next month (unless you get a higher limit). Requests return HTTP 429 `rate_limit_error` with NO `retry-after` header and `error.details.error_code: "enforced_spend_limit_reached"` (Messages API). SDK auto-retries keep failing.
5. [Documented] Reaching a spend limit YOU set returns HTTP 400 `invalid_request_error`, message starting "You have reached your specified API usage limits" (or "...workspace API usage limits"), stating when access resumes. (Claude Code workspace is the exception: 429 with `retry-after`.)
6. [Documented] Messages API limits per model: RPM, ITPM, OTPM. Start tier — Opus 5.5, Sonnet 5.5, Haiku 5.5 each: 4,000 RPM / 2,000,000 ITPM / 400,000 OTPM. Build — each: 10,000 RPM / 5,000,000 ITPM / 1,000,000 OTPM. Scale — each: 13,000 RPM / 10,000,000 ITPM / 2,000,000 OTPM. Each 5.5 model has its own bucket (not shared with 4.x or 5 models).
7. [Documented] Token bucket algorithm: capacity replenishes continuously rather than resetting at fixed intervals; limits may be enforced over shorter intervals (60 RPM may be enforced as 1 request/second), so short bursts can 429.
8. [Documented] Cache-aware ITPM: only `input_tokens` + `cache_creation_input_tokens` count toward ITPM; `cache_read_input_tokens` do NOT. Example: 2,000,000 ITPM with an 80% cache hit rate ≈ 10,000,000 total input tokens/min. ITPM is estimated at request start and adjusted.
9. [Documented] OTPM counts only actual generated tokens in real time; `max_tokens` does not factor in, so a high `max_tokens` has no rate-limit downside.
10. [Documented] Ramp limits: a sharp increase (even a few-seconds burst) can 429 while under ITPM/OTPM. Ramp limit = recent per-minute peak + a step; rises with successful usage up to the rate limit, decays after quiet periods, never below a starting amount. Input and output counted separately; cache reads don't count. `error.details.error_code: "ramp_limit_exceeded"`. Advice: honor `retry-after`, hold traffic where it succeeds, grow at most one step per minute, spread bulk jobs. Batches are exempt.
11. [Documented] Rate limits are shared across `inference_geo` values ("us" and "global" draw from the same pool).
12. [Documented] Message Batches limits (all models shared): Start 1,000 RPM / 200,000 queued batch requests; Build 2,000 / 300,000; Scale 4,000 / 500,000; max 100,000 requests per batch.
13. [Documented] Response headers: `retry-after` (seconds; not on every 429, never on the spend-cap 429); `anthropic-ratelimit-requests-{limit,remaining,reset}`; `anthropic-ratelimit-tokens-{limit,remaining,reset}` (most restrictive limit in effect, including workspace limits); `anthropic-ratelimit-input-tokens-*` and `anthropic-ratelimit-output-tokens-*`; remaining values rounded to nearest thousand; resets are RFC 3339 timestamps. `anthropic-workspace-id` shows which workspace the request counted against.
14. [Documented] Error types: 400 `invalid_request_error`; 401 `authentication_error` (also "CORS requests are not allowed for this Organization" when a browser `Origin` header is present — fix by calling from your own back end); 402 `billing_error`; 403 `permission_error`; 404; 409 `conflict_error`; 413 `request_too_large` (Messages 128 MB); 429 `rate_limit_error`; 500 `api_error`; 504 `timeout_error`; 529 `overloaded_error` ("can occur when the API experiences high traffic across all users"). Errors are JSON with `error.type`, `error.message`, and `request_id`; optional `error.details.error_code`.
15. [Documented] SDK retries: default 2 retries (3 attempts). Follows `x-should-retry` header if present; otherwise retries connection errors, timeouts, 408, 409, 429, and ≥500. Waits `retry-after` if present, else exponential backoff 0.5–8 s. Configure via `max_retries` (TS `maxRetries`); 0 disables. Without SDK: implement `x-should-retry` / `retry-after` handling with backoff and a retry cap.
16. [Documented] Streaming: an error can arrive mid-stream after an HTTP 200 (SSE error event); the SDK does not retry errors inside a stream. Use streaming or batches for long requests (SDK refuses non-streaming requests expected to exceed 10 minutes).
17. [Documented] Every response has a `request-id` header (e.g., `req_...`) — log it for support.
18. [Documented] Request higher limits via "Request tier increase" on the Console Rate limits page or Anthropic support.
19. [Inferred] For the app backend: the Start-tier $500/month cap is a hard ceiling for a new solo developer — plan monetization and per-user quotas so that total spend stays below it, and treat `enforced_spend_limit_reached` as a non-retryable outage (show a friendly "service busy" message, stop retrying). Distinguish it from `ramp_limit_exceeded` and ordinary 429s in code.
20. [Inferred] Your own per-user rate limiting must sit in the proxy; Anthropic's limits are organization-wide, so one abusive user can exhaust everyone's RPM/ITPM. Launch-day traffic spikes can trip ramp limits; a request queue with gradual ramp helps.

## Key quotes
- "The API uses the token bucket algorithm to do rate limiting. This means that your capacity is continuously replenished up to your maximum limit, rather than being reset at fixed intervals." — https://platform.claude.com/docs/en/api/rate-limits
- "**The API’s default ITPM rate limits count only uncached input tokens.**" — https://platform.claude.com/docs/en/api/rate-limits
- "The error type is `rate_limit_error`, the same as for a rate limit, but the response has no `retry-after` header. Retrying, including the SDK’s automatic retries, fails until access resumes." — https://platform.claude.com/docs/en/api/rate-limits
- "After a sharp increase in usage, requests can return a 429 error even while you’re under your ITPM and OTPM rate limits." — https://platform.claude.com/docs/en/api/rate-limits
- "A 529 error can occur when the API experiences high traffic across all users." — https://platform.claude.com/docs/en/api/errors

## Limitations or bias
- Vendor docs. Evaluation-tier limits, ramp-limit step sizes and starting amounts are not published ("vary by model and can change").
- No deposit amounts or tier-advancement criteria are given; earlier versions of these docs used credit-purchase thresholds, which this page no longer lists — don't rely on older numbers.

## Summary-only items
- Errors page: SDK error-type tabs per language and the "Common validation errors" subsections (prefill not supported, thinking cannot be disabled, forced tool use not supported, etc.) were seen as headings only.

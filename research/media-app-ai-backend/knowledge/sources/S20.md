## Learned points
1. [Documented] MAS requirement: "The app does not hardcode sensitive data in the application package." Mapped to MASVS v2 MASVS-STORAGE-1 (v1: MSTG-STORAGE-1, MSTG-CODE-2) and CWE-312, CWE-321, CWE-540, CWE-798. Profiles tagged L1 and L2, Android and iOS.
2. [Documented] Overview: the weakness is sensitive data embedded in the APK/IPA "where anyone who downloads the package can recover it". Covers API keys and secrets for first- or third-party services, credentials (passwords, session tokens), and cryptographic keys embedded instead of generated in a platform keystore.
3. [Documented] It also covers developer leftovers: staging/integration URLs, developer emails and usernames, and source or build files left in the package (e.g. .swift, .cpp, map files). Debug artifacts (verbose logging, backdoors, hidden switches) are covered under a separate resilience weakness.
4. [Documented] Modes of introduction: app source code; app assets and resources (config files, manifests, property lists, string resources, bundled files); libraries (first-party, third-party or transitive dependencies); build and developer leftovers.
5. [Documented] Impact, financial loss: "Attackers can abuse compromised API keys to make unauthorized billed API calls (e.g., AI/ML services), resulting in unexpected charges to the app owner." AI/ML services are named explicitly.
6. [Documented] Other impacts: access to backend services leading to disruption, "policy-violation suspensions", or denial of service; decryption of protected data with extracted keys; unlocking paid features or restricted content with hardcoded keys.
7. [Documented] Mitigation 1, proxy static secrets through middleware: if a stateful API service is not viable, put an API proxy or gateway between app and API so the static secret stays server-side; use JWT and JWS as appropriate.
8. [Documented] Mitigation 2, stateful API services: prefer services with authentication, client validation and session controls; dynamic tokens that expire "after a reasonably short time (e.g., 1 hour)"; error handling and logging to detect unauthorized access; consider OAuth 2.0 and AppAuth.
9. [Documented] Mitigation 3, retrieve secrets at runtime from a Key Management Service behind middleware, after validating device and app integrity, over a secure pinned channel. Mitigation 4, if a secret must be hardcoded, give it minimum permissions and restrictions.
10. [Documented] Mitigation 5, store keys and auth material in the hardware-backed platform keystore (Android Keystore, iOS Keychain). Mitigation 6, regularly audit code and dependencies for hardcoded secrets and leftovers (gitleaks is named) and strip build artifacts from release packages.
11. [Documented] Mitigation 7, harden only as a last resort: white-box cryptography, code/resource obfuscation and RASP "deter but do not prevent extraction and must not replace the mitigations above".
12. [Documented] The MASTG has no tests for this weakness yet; the page invites test proposals via the OWASP mastg GitHub issues.
13. [Inferred] For the React Native + Expo app: the Claude API key must never be in the JS bundle, `app.json`/`app.config` extra fields, or any `EXPO_PUBLIC_` variable, because anything bundled ships in the APK/IPA. The app should call the developer's own backend proxy, which holds the key server-side (mitigation 1), and the proxy should authenticate users with short-lived tokens (mitigation 2).
14. [Inferred] Obfuscation of a bundled key is explicitly not an acceptable substitute; the "unauthorized billed API calls (e.g., AI/ML services)" impact is exactly the denial-of-wallet risk in S10.

## Limitations or bias

- No page date; content may change as MASWE evolves.
- Generic mobile guidance; it does not mention React Native, Expo or `EXPO_PUBLIC_` variables (points 13–14 are inference).

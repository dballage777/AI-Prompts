## Learned points
1. [Documented] API routes are files in the app directory ending in `+api.ts`. For example, `src/app/hello+api.ts` serves `/hello`. You export `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` or `OPTIONS`. Unsupported methods return `405`. A thrown error returns `500`. Requests and responses use the standard `Request` and `Response` objects. Routes "should be executed in a WinterCG-compliant environment."
2. [Documented] You need `"web": {"output": "server"}` in app.json. SDK 58+ enables API routes by default with server output. With `output: "static"`, you add `["expo-router", {"apiRoutes": true}]`. Platform-specific filenames such as `hello+api.web.ts` do not work.
3. [Documented] Secret handling: route handlers run in a sandbox isolated from client code. A secret in a `+api.ts` file, or in any file that file imports, is not included in the client bundle. But client code that imports code containing a secret is bundled, and this applies to all files in `src/app`. The stripping happens in `expo/metro-config`, which must be used in `metro.config.js`. Server routes can read all environment variables, not just `EXPO_PUBLIC_` ones.
4. [Documented] How native apps call routes: relative `fetch('/hello')` resolves to the dev server in development. In production you must deploy the server to a secure host and set the `origin` option of the `expo-router` config plugin (for example `"origin": "https://example.com/"`). Native deployment is labelled an alpha feature.
5. [Documented] `EXPO_UNSTABLE_DEPLOY_SERVER=1` (experimental) makes Expo Build deploy a versioned server and set `origin` automatically. It requires that `origin` is not already set, does not support `app.config.js`/`app.config.ts`, can be skipped with `EXPO_NO_DEPLOY=1`, logs to `.expo/logs/deploy.log`, and does not run in `EXPO_OFFLINE` mode.
6. [Documented] Deploy commands: `npx expo export --platform web` (add `--no-ssg` for server code only), then `eas deploy`. Test locally with `npx expo serve`. For other hosts (Bun, Express, Netlify, Vercel), `expo-server` (SDK 54+) provides adapters. Third-party adapters "are subject to breaking changes", and `expo-server` does not load `.env` files.
7. [Documented] `expo-server` runtime helpers (SDK 54+): `StatusError(status, msg)`, `origin()`, `environment()`, `runTask()` (like `waitUntil`, does not delay the response), `deferTask()` (runs after the response), and `setResponseHeaders()`. Middleware lives in `+middleware.ts`. The docs' middleware example sets `Retry-After` "for rate limiters".
8. [Documented] Known limits of the API routes beta: no dynamic imports, because all code is bundled into one file. Libraries with platform binaries (for example `sharp`) cannot be used. ESM is transpiled to CommonJS.
9. [Documented] Expo Hosting runs on Cloudflare Workers (V8 isolates, not Node.js processes) with partial Node.js compatibility. Supported: `node:crypto` (some deprecated algorithms missing), `node:stream`, `node:stream/web`, `node:fs` (in-memory only), and `node:http`/`node:https` (client only). Not supported: `node:worker_threads`, `node:readline`, `node:punycode`. Node module resolution is unsupported. Modules not listed "are unavailable or unsupported". `process.env` is populated with Expo Hosting environment variables.
10. [Documented] Streaming: the API routes page links a video titled "Handle Requests & Stream Data", but its text has no streaming code sample. The expo SDK page (S16) says "Expo Hosting server runtime also includes support for the standard web streams API". The worker runtime lists `node:stream/web` as supported. A route can therefore return `new Response(readableStream)`. The exact SSE pattern is not shown on these pages.
11. [Documented] Expo Hosting suits "Use API routes or server functions", but the docs mark "Mobile-only project with no web component" as ✗ (not recommended), along with "Full Node.js runtime compatibility".
12. [Documented] Deployments are immutable. Each one gets a unique preview URL. Aliases such as `production` can be reassigned, and `eas deploy:alias --prod --id=<deploymentId>` rolls back instantly. Custom domains require a paid plan, one per project.
13. [Documented] Monitoring in the dashboard covers crashes (grouped, with stack traces), logs (`console.*`), and requests (status, browser, region, duration). Every response has a `Cf-Ray` header whose first part is the request ID. Under high traffic, recorded data is downsampled.
14. [Documented] Caching: routes can return `Cache-Control`, `s-maxage` or `CDN-Cache-Control`. GET/HEAD responses to requests without an `Authorization` header are automatically publicly cacheable. POST responses are cacheable only when marked `public` and the body is under 1MB, and the cache key is URL plus body. "Cached requests **still count**" toward billed requests.
15. [Documented] Hosting pricing (expo.dev/pricing, seen 2026-11-25). All plans: 100,000 requests per month, 1,000,000 CPU-ms, 1 GB storage. Paid plans then pay $2 per 1M requests, $0.04 per 1M CPU-ms, $0.04 per GB. Per-request limits: Free = 10 CPU-ms and 10 subrequests. Starter, Production and Enterprise = 30,000 CPU-ms and 10,000 subrequests. Aliases: 5 on Free, 200 on paid plans. Log retention: 7 days on Free, 3 months on paid plans. Plan prices: Free $0, Starter $19/mo + usage, Production $199/mo + usage.
16. [Inferred] On the Free plan, the 10-subrequest limit is a hard blocker for this app. One recommendation turn involves a Claude call plus several AniList/TVmaze/Wikidata verification calls (each one an outbound subrequest), and possibly several Claude tool-use round trips. The 10 CPU-ms limit is also tight for JSON parsing and signature checks. Plan for at least Starter ($19/mo) or a different host. Note that the per-request limit is CPU time, not wall-clock time; whether a long streaming Claude response also has a duration cap is not stated on these pages.
17. [Inferred] The `origin` setup is the bridge between native and server, and it is alpha. Pin `origin` to a stable production alias or custom domain rather than a per-deploy preview URL, so shipped binaries keep working after redeploys.
18. [Inferred] Because GET responses without `Authorization` are auto-cacheable at the CDN, per-user AI endpoints should be POST with an auth header, or send `Cache-Control: private, no-store`, so one user's recommendations are never served to another.

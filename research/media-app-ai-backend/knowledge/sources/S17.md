## Learned points
1. [Documented] Purpose: `@expo/app-integrity` "helps your server tell the difference between" your real app on a real device and "Anything else (modified apps, scripts, emulators)". It wraps Google Play Integrity (Android) and Apple App Attest (iOS). Install with `npx expo install @expo/app-integrity`. The page says it is available on Android and iOS and is "Included in Expo Go". An example project is available: `npx create-expo-app --example with-app-integrity`.
2. [Documented] Android uses Play Integrity's Standard request flow. First, one-time: `prepareIntegrityTokenProviderAsync(cloudProjectNumber)` at launch or in the background. Then, per action: `requestIntegrityCheckAsync(requestHash)` returns a token string, where `requestHash` is "a hash unique to the specific user action being verified".
3. [Documented] If a token provider is used too long it expires, and the next request fails with `ERR_APP_INTEGRITY_PROVIDER_INVALID`. Handle it by calling `prepareIntegrityTokenProviderAsync` again. The Standard flow supports Android 5.0 (API 21) and higher, per the linked Google doc summary.
4. [Documented] Android server side: the backend must decrypt and verify the integrity token following Google's Standard-flow guide, then decide how to act on the verdict (device, app and account validity). Setup requires enabling integrity responses in Play Console, as described in Google's setup guide.
5. [Documented] Android extras: `isHardwareAttestationSupportedAsync()`, `generateHardwareAttestedKeyAsync(keyAlias, challenge)`, and `getAttestationCertificateChainAsync(keyAlias)`, which returns base64 X.509 certificates for server validation. The docs describe this as usable "on GrapheneOS and other secure Android distributions".
6. [Documented] iOS configuration: add the App Attest capability in Xcode (Signing & Capabilities), which adds the entitlement. The app needs an App ID registered on the Apple Developer site. App Attest is not supported on iOS Simulator. Most app extensions are unsupported (only watchOS 9+ extensions are).
7. [Documented] iOS flow, step 1: check `AppIntegrity.isSupported`, and if false, "gracefully bypass the service". Step 2: `generateKeyAsync()` returns a `keyId`. The private key is created in the Secure Enclave and can never be read. Persist the `keyId`, because there is "no way to get the identifier later". Create one key per user account per device, and do not reuse keys across users.
8. [Documented] iOS flow, step 3: get a one-time challenge from your server, "at least 16 bytes long". Step 4: `attestKeyAsync(keyId, challenge)` returns an attestation object. Send it and the `keyId` to the server for verification. On `ERR_APP_INTEGRITY_SERVER_UNAVAILABLE`, retry later with the same key. On any other error, discard the key and generate a new one.
9. [Documented] iOS flow, step 5: once attestation is verified, the server can require assertions. The app gets a fresh one-time challenge, builds the request payload (the example includes `action`, ids and `challenge`), and calls `generateAssertionAsync(keyId, JSON.stringify(request))`. The app sends the assertion and the client data to the server. If verification fails, "it's your responsibility to decide how to handle the request."
10. [Documented] Assertions have no count limit, but Apple and Expo suggest using them at "sensitive moments" (for example premium content downloads). Apps with millions of daily active users should ramp attestation gradually, following Apple's "Preparing to use the app attest service" guide.
11. [Documented] Keys survive app updates but not reinstallation, device migration or restore from backup. Then you must generate a new key and attest again. Keep key generation to those events and to new users, because a low key count per device helps fraud detection.
12. [Documented] The server-side verification logic is not provided by Expo. For iOS, the page points to Apple's "Validating apps that connect to your server" and "Assessing fraud risk". For Android, it points to Google's decrypt-and-verify guide.
13. [Inferred] What the server for this app must do. (a) Issue random one-time challenges (16+ bytes), store them briefly and reject reuse. (b) iOS: verify the attestation once per key, store the public key and `keyId` tied to the user/install, then verify assertions (signature over the client data, counter, challenge) on expensive calls such as `/recommend`. (c) Android: verify the Play Integrity token through Google's server API and check the `requestHash` binding and verdict fields. (d) Decide a policy for unsupported devices or failures: allow with a lower quota rather than hard-block, since the docs say to bypass gracefully when unsupported.
14. [Inferred] App integrity raises the cost of scripted abuse of the Claude proxy but does not replace per-user auth, rate limiting and spend caps. A genuine device running the genuine app can still be scripted or abused at human speed.
15. [Inferred] Because App Attest needs an entitlement and does not work on the simulator, test on a physical iOS device with a development build. The docs' "Included in Expo Go" note does not establish that App Attest works inside Expo Go.

## Limitations or bias
- This is a wrapper's docs. Quotas and pricing for Play Integrity (Google's daily request limits) and verdict field names live in Google's and Apple's docs, which were not read. No server code is given.
- The page does not say when the library was introduced or its stability status.

## Summary-only items
- Android API-level support (5.0 / API 21) comes from the Expo page's one-line summary of a linked Google doc, not from the Google doc itself.

## Best used for
- Designing the device and app attestation layer of abuse prevention for the Claude proxy: exact client methods, the challenge, attest and assert sequence, error handling, and the server's responsibilities.

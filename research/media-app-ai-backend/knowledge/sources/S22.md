## Learned points
1. [Documented] The current pattern is the `withSupabase` wrapper from `npm:@supabase/server@1`, with four auth modes: `'user'` (valid user JWT on `Authorization`), `'secret'` (default secret key on `apikey`), `'publishable'` (default publishable key on `apikey`), and `'none'` (no check, for signed webhooks). Modes can be combined (`auth: ['user','secret']`), and `ctx.authMode` reports which mode matched. Named keys use `'secret:<name>'` or `'secret:*'`.
2. [Documented] `ctx.supabase` is scoped to the caller's RLS policies; `ctx.supabaseAdmin` bypasses RLS. Cited failure mode: querying a shared table through `supabaseAdmin` without filtering by the caller's ID "returns every user's rows". `ctx.userClaims` holds id, email and role.
3. [Documented] `verify_jwt = true` is the default; the platform validates the JWT before the handler runs. It is turned off per function in `supabase/config.toml` (`[functions.name] verify_jwt = false`) for webhooks and service-to-service calls. The docs warn that turning it off "to clear a 401 during development" leaves the wrapper as the only check.
4. [Documented] Critical caveat: for migration compatibility, `verify_jwt` also accepts publishable and secret keys (on either header). "The check alone doesn't authenticate a caller that sends only an API key." The new `sb_publishable_...` and `sb_secret_...` keys are not JWTs. Send user tokens on `Authorization: Bearer <user-jwt>` and keys on `apikey`.
5. [Documented] Key semantics: the publishable key (and legacy `SUPABASE_ANON_KEY`) is "Safe to use in a browser when you have Row Level Security enabled". Secret keys (and legacy `SUPABASE_SERVICE_ROLE_KEY`) bypass RLS, so they belong in Edge Functions "and never in a browser". The legacy pattern passes the `Authorization` header into `createClient` with the anon key and calls `auth.getUser(token)`.
6. [Documented] Injected environment variables: `SUPABASE_URL`, `SUPABASE_DB_URL`, `SUPABASE_PUBLISHABLE_KEYS` and `SUPABASE_SECRET_KEYS` (JSON dictionaries), and `SUPABASE_JWKS`. Hosted functions also get `SB_REGION`, `SB_EXECUTION_ID` and `DENO_DEPLOYMENT_ID`.
7. [Documented] Secrets: local secrets go in `supabase/functions/.env` (gitignore it). Production: `supabase secrets set --env-file .env` or `supabase secrets set NAME=value`, and `supabase secrets list`. Functions "read a new secret immediately", with no redeploy. Creating or deleting secrets needs the Owner or Administrator role. Read with `Deno.env.get('NAME')`. Names cannot start with `SUPABASE_`.
8. [Documented] Runtime limits: 256 MB memory. Wall-clock duration 150 s on the Free plan and 400 s on paid plans. CPU time 2 s per worker (excluding async I/O). Request idle timeout 150 s, after which a 504 is returned if no response has started.
9. [Documented] Platform limits: function size 20 MB (CLI bundled) or 5 MB (server-side bundled). Functions per project: Free 100, Pro 1000, Team 2000. Log message 10,000 characters max; 100 log events per 10 s. Nested calls: 30 requests per trace within 60 s. Secrets: 100 per project, 48 KiB each. Outbound ports 25 and 587 are blocked. No Web Worker or `vm` API; multithreaded Node libraries (sharp, libvips) are unsupported.
10. [Documented] Rate-limiting example page: Supabase recommends Upstash's HTTP/REST Redis client for serverless rate limiting and notes you "can even rate limit based on the user ID from Supabase Auth". The code itself is only on GitHub (not read).
11. [Inferred] For this app, the publishable key ships in the Expo app and is public, so `verify_jwt` alone does not stop a scripted caller who copies it. The Claude proxy function should use `withSupabase({ auth: 'user' })` (or verify the JWT and read `sub` itself) and rate-limit by that user ID. Anonymous sign-in users would still get a JWT; whether that is acceptable for abuse control is a design decision not covered here.
12. [Inferred] A multi-turn tool-use run (Claude plus AniList/TVmaze/Wikidata calls) must finish within 150 s wall clock on Free (400 s paid) and must start streaming before the 150 s idle timeout. The 2 s CPU limit is rarely the bottleneck because waiting on network I/O does not count toward it.
13. [Inferred] Store the Anthropic key with `supabase secrets set ANTHROPIC_API_KEY=...`, never as an `EXPO_PUBLIC_` variable.

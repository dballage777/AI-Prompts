## Learned points
1. [Documented] Expo CLI auto-loads variables prefixed `EXPO_PUBLIC_` from `.env` files and replaces every reference `process.env.EXPO_PUBLIC_[NAME]` in your JS with the literal value at bundle time. The value is baked into the app bundle.
2. [Documented] Inlining only works with static dot notation: `process.env.EXPO_PUBLIC_KEY` is inlined. `process.env['EXPO_PUBLIC_KEY']` and destructuring `const {EXPO_PUBLIC_X} = process.env` are "invalid and will not be inlined". Code inside `node_modules` is not affected, "for security purposes".
3. [Documented] Explicit warning: do not store private keys or other sensitive info in `EXPO_PUBLIC_` variables. They are "visible in plain-text in your compiled application". The security section says end users "have access to all of the code and embedded environment variables in your app" and links to the React Native security guide (S24).
4. [Documented] `.env` file priority by mode. Development: `.env.development.local`, `.env.local`, `.env.development`, `.env`. Production: `.env.production.local`, `.env.local`, `.env.production`, `.env`. In SDK 58+, other files (for example `.env.staging`, `.env.test`) are not loaded. Recommended `.gitignore` entry: `.env*.local`.
5. [Documented] SDK 58+: each command sets `NODE_ENV` to its own mode and overrides yours. `npx expo start` = development (`--no-dev` gives production). `npx expo export` = production. `eas update` calls `npx expo export`, so it always runs as production. Expo suggests `eas env:pull` to switch environments instead of relying on `NODE_ENV`.
6. [Documented] Kill switches: `EXPO_NO_DOTENV=1` stops `.env` loading. `EXPO_NO_CLIENT_ENV_VARS=1` stops inlining into the client bundle.
7. [Documented] Expo Services environment variables are stored on Expo servers (set with `eas env:set` or the expo.dev dashboard), separated into `development`, `preview` and `production`. Custom environment names require Enterprise or Production plans. Scope is project-wide or account-wide. Types are strings or files.
8. [Documented] There are three visibility levels. Plain text: visible on the website, in EAS CLI and in logs. Sensitive: obfuscated in Build/Workflows job logs, can be revealed on the website by toggle, readable in EAS CLI. Secret: "Not readable outside of the Expo servers", including the website and EAS CLI, and obfuscated in logs.
9. [Documented] Secret visibility does not protect anything embedded in the app: "Secrets do not provide any additional security for values that you end up embedding in your application itself." Secrets exist to change how a build or workflow job runs (example: `NPM_TOKEN`). The docs also say "anything that is included in your client-side code should be considered public."
10. [Documented] Expo Hosting accepts only plain text and sensitive variables: "Secrets cannot be deployed with Expo Hosting." Secret-type variables are also unavailable during `eas update` and during build-config resolution in EAS CLI.
11. [Documented] How server code gets secrets: code in API routes (`+api.ts`) runs on the server, and there "you can safely use sensitive environment variables such as API keys and tokens." Server-side variables are not inlined. They are uploaded with the deployment by `eas deploy --environment <env>`. Variables loaded with `--environment` override `.env` and `.env.local`.
12. [Documented] Deploy order for client and server variables together: `eas env:pull --environment production`, then `npx expo export --platform web` (inlines `EXPO_PUBLIC_` into frontend code), then `eas deploy --environment production`.
13. [Documented] "Environment variables are per deployment, and deployments are immutable." After changing a variable (for example, rotating an API key), you must re-export and re-deploy.
14. [Documented] SDK 55+: `eas update` requires `--environment`. With the flag, only that Expo Services environment's plain text and sensitive values are inlined, and local `.env` files are ignored. SDK 54 and earlier fall back to `.env` when the flag is omitted.
15. [Documented] Expo Build picks the environment from the `environment` field in the `eas.json` build profile. Without it: `production` if `distribution` is `store`, `development` if `developmentClient` is true, otherwise `preview`.
16. [Inferred] For this app, the Claude API key (and any AniList/TVmaze keys, if those services need one) should be server-only variables with no `EXPO_PUBLIC_` prefix. On Expo Hosting that means "sensitive" visibility, because "secret" cannot be deployed there. Sensitive values stay readable in EAS CLI and on the dashboard by toggle, so access to the Expo account effectively equals access to the key. Protect the account with 2FA.
17. [Inferred] Only non-secret configuration belongs in `EXPO_PUBLIC_` variables (for example the API base URL and feature flags). Any value with that prefix should be treated as published.
